Purpose: To organize the operating philosophy, safety boundaries, verification, stopping conditions, and handoff methods for assigning long-running analysis and implementation work to Codex. The primary target is analysis and implementation performed as a personal hobby.

This document is not a finished AGENTS.md. It is a design document that preserves lessons learned from actual operation and the reasons behind them. Each project should distill only the necessary items into AGENTS.md and more detailed rules.

Part I — Overview and Design Principles

1. Core Idea — Design the Workplace, Not the Prompt

Using Codex is not merely asking an AI to perform work. The goal is not to provide detailed instructions through a long prompt every time, but to prepare an environment in which work remains stable even when the request itself is short.

The basic idea is to treat conversation context as volatile working memory, and Markdown files and working folders as nonvolatile external memory.

Conversation context    = volatile working memory
Markdown                = nonvolatile external memory
Git                     = change history and rollback mechanism when needed

On top of this external memory, place conventions, Sandbox / Approval, tools, verification methods, and recovery procedures. The design target is not a single prompt, but the entire working environment, including memory, conventions, authority, tools, verification, and recovery.

The core idea is not that “everything will work if Codex is smart enough,” but to build an environment in which Codex can lose its way without losing state, reread the rules and evidence, and continue working.

2. Do Not Build a Large Operational Framework Up Front

The current primary use case is analysis and implementation work on a local PC that finishes within several hours to roughly one day. Start with AGENTS.md and the minimum necessary procedures.

Only when an accident, drift, or inconvenience occurs should the cause be examined, and a decision made about whether recurrence should be prevented through Markdown, configuration, tests, or technical boundaries. If the existing mechanisms already recovered correctly from an accident, a new rule is not necessarily required.

Incident → identify cause → add only the recurrence prevention that is needed

Grow the operational framework from real use in this way.

3. Three Perspectives

① Building a “Workplace” for Long-Running Work

  • Record the state of long-running work so it can be resumed.
  • Separate workflow from working notes.
  • Define which tools are permitted.
  • Do not make one enormous AGENTS.md carry everything.

② “Division of Responsibility” Between Humans and AI

  • Approval is not distrust; it is a division of responsibility.
  • Separate confirmation conditions by impact, not by operation name.
  • Treat stopping, consultation, and return as normal connections in the workflow.
  • If return is treated as lack of capability, the Agent is pushed toward forced completion.

③ “Building Security Design”

  • Begin from a state where nothing is allowed.
  • Open only the capabilities that are needed.
  • Do not treat Sandbox as a single concept; decompose it into read / write / execute / shell / network / secrets / approval.

This document treats these not as competing philosophies, but as different layers.

4. Use the Organizational Metaphor as an Aid to Understanding

The overall operation is easier to understand when viewed as a small technical organization.

In this view, Codex is not merely “the person being instructed.”

Human           : owns purpose, acceptable risk, and final judgment
Codex / Agent   : advances investigation and implementation
Rules/boundaries: determine what may be done and how far capability extends
Verification    : independently checks whether the result is correct
Records         : preserve state and carry it into the next work session

The value of this metaphor is that it makes it possible to design capability, authority, responsibility, verification, and records separately.

The important point is not to collapse all of these into the ability of one “smart AI.”

  • Being able to do work is different from being allowed to do it.
  • Being allowed to do work is different from the result being correct.
  • The result being correct is different from being able to resume next time.
  • The AI being capable of making a judgment is different from the human carrying final responsibility.

The center of this design is not increasing AI capability itself, but designing the responsibility boundaries through which judgment, verification, stopping, return, and records flow.

5. Minimum Principles to Adopt at Present

Even if everything is not implemented from the beginning, preserve the following principles.

  1. Do not turn Approval into a click ritual.

    • Automate routine work appropriately and return to the human only at genuinely important boundaries.

  2. Do not treat Sandbox as a single concept.

    • Separate its boundaries and verify actual behavior.

  3. Do not close correctness judgment inside the AI itself.

    • Use independent measured values that are not merely the AI's own judgment.

  4. Human guesses are hypotheses too.

    • Separate observation from inference.

  5. When something fails, return to primary sources.

    • Prefer primary sources over generating many alternative explanations.

  6. Failure is a normal termination path.

    • Rather than forcing completion under uncertainty, return to the human at the point where judgment is needed.

  7. Do not send analysis information outside.

    • Analysis information must not be transmitted externally.

Part II — Documents, External Memory, and Knowledge Management

6. Keep AGENTS.md a Short “Constitution”

Place in AGENTS.md only the rules and assumptions worth reading every time.

Main Subjects

  • Network policy
  • Areas where writing is prohibited
  • Handling of images, text, and similar content
  • Basic principles for stopping, consultation, and return
  • Basic principles for failure
  • Work locations and artifact placement
  • Build environment to use

Give Facts Needed for Judgment, Not Merely Commands

Do not duplicate information that can easily be inferred from the code or work target itself.

What has value is information that Codex cannot observe by itself, or assumptions that are unlikely to be reflected in judgment from ordinary working context alone.

Rather than adding prohibitions, provide the facts Codex needs in order to choose for itself.

If commands, work logs, and confirmed knowledge begin to mix together, separate them.

7. Separate the Roles of OPERATIONS.md, analysis, and spec

While AGENTS.md carries rules that must always be followed, the remaining three documents divide responsibility for work procedures, unconfirmed knowledge, and confirmed knowledge. The purpose is not to increase the number of documents, but to avoid mixing information with different lifetimes and confidence levels.

OPERATIONS.md                = repeatable work procedures and state transitions
memo/<tool>_analysis.md      = unconfirmed analysis state
memo/<tool>_spec.md          = verified, confirmed knowledge

OPERATIONS.md — How Work Proceeds

Place the repeatable flow of starting work, building, verification, finishing, stopping, and recovery here. Do not make it depend on the analysis results of a particular tool.

Put the assumption “which build environment to use” in AGENTS.md, and put the procedure for actually building with that environment in OPERATIONS.md.

<tool> — Separate Knowledge by Analysis Tool

<tool> represents the tool used for analysis. Keep an analysis / spec pair for each tool, and advance analysis, implementation, and verification while preserving the distinction between confirmed and unconfirmed information.

memo/<tool>_analysis.md — Preserve What Is Still Being Thought Through

Store observed facts, hypotheses, supporting basis, attempts, failures, contradictions, and unresolved items from the analysis process. Speculation is allowed, but it must remain distinguishable from confirmed facts.

memo/<tool>_spec.md — Preserve Only What Has Been Confirmed

Store verified formats, meanings of values, constraints, transformation rules, and confirmed behavior. Treat this as the authoritative technical knowledge on which implementation may depend. Preserve the basis for those conclusions and the still-unverified range as well.

The following is one example for the local analysis work discussed in this document.

The basic flow is:

Read the target EXE → accumulate findings in analysis → verify → reflect them in the executable form of <tool> → verify → promote to spec

This is the intended sequence.

Basic Project Structure

The main folders used in this document are divided by role as follows.

project/
  memo/   # analysis knowledge such as analysis / spec
  org/    # originals and primary sources
  work/   # implementation, experiments, and generated artifacts

Create org/ and work/ when they become necessary in an actual project.

8. Do Not Reduce Information; Delay Reading It Until Needed

Do not collect too much detail into AGENTS.md or OPERATIONS.md.

When independently repeatable work increases, separate it into Markdown files or Skills by work unit, and leave only a map in the higher-level documents that leads to the information when it is needed.

The AI should follow only the specifications, procedures, recovery methods, and failure handling required for the current work.

Do not reduce the information that is stored; reduce the information brought into the active working context.

9. Use analysis.md / spec.md to Separate Unconfirmed and Confirmed Knowledge

Place speculation and unverified items from analysis in memo/<tool>_analysis.md, and promote only verified knowledge to memo/<tool>_spec.md.

Example analysis entry:

Hypothesis: opcode 0x17 may be a conditional branch
Basis: the program counter (PC) changes immediately after a 2-byte argument
Confidence: low
Falsification condition: the branch destination does not change even when the target flag changes
State: unverified

Example spec entry after verification:

opcode: 0x17
meaning: conditional branch
argument: 2 bytes
behavior: when the condition is true, the PC moves to the position indicated by the argument;
          when false, execution proceeds to the next instruction
verification: changed the condition and measured both branch outcomes

Principles:

  • Do not prohibit speculation; isolate it from confirmed facts.
  • Unverified information must not gain confidence merely because it crosses process or agent boundaries; treat it as hypothesis until verified.
  • When practical, attach the basis, confidence level, and falsification conditions to hypotheses.
  • Rejected hypotheses may be deleted, but keep them as records if the same mistake is likely to recur.

10. Analysis and Greenfield Development Discard History Differently

In analysis work, there are stable primary sources outside the model—ASM, original data, measured values, diffs, and so on—and reasoning is a foothold toward a confirmed specification. Even rejected hypotheses can be reused as explored territory showing that “this direction contradicted measurement,” so there is strong value in preserving intermediate reasoning richly in memo/<tool>_analysis.md.

By contrast, in greenfield application development, requirements and design can themselves change along the way. If every past judgment is preserved, obsolete design reasons remain in context and may pull the AI back toward outdated assumptions.

Analysis:       accumulate reasoning → promote confirmed facts into spec
Greenfield dev: accumulate reasoning → design history grows

For that reason, in greenfield development it is better to compress history into the current decision and preserve the following, rather than storing every log.

  • The decision currently adopted
  • Why that decision was made
  • Important rejected alternatives that are likely to be reconsidered
  • Unresolved items

In short, analysis “accumulates without deleting,” while greenfield development “compresses toward the current decision.”

11. Separate the Worker from the Maintainer of the Working Environment

Documents that define Codex's working environment itself—such as AGENTS.md, OPERATIONS.md, and this document—should be maintained through a maintenance path separate from ordinary analysis and implementation.

In the current operation described here, ChatGPT is used to review and edit these documents.

By contrast, memo/<tool>_analysis.md / memo/<tool>_spec.md are external memory for the analysis itself, so Codex may update them while working.

memo/_analysis_template.md / memo/_spec_template.md are not analysis records. They are maintenance templates that define the roles and structure of analysis / spec. Codex may reference and copy them, but must not modify the templates themselves.

Updated by Codex
  memo/<tool>_analysis.md
  memo/<tool>_spec.md

Referenced and copied by Codex
  memo/_analysis_template.md
  memo/_spec_template.md

Accepted or rejected by the human, then maintained on the ChatGPT side
  CODEX_WORKPLACE_DESIGN.md
  AGENTS.md
  OPERATIONS.md
  memo/_analysis_template.md
  memo/_spec_template.md

If Codex determines that an operations document should be changed, it should not modify it directly. Instead, it returns the problem and a proposed change to the human. The human decides whether to adopt it, and any required editing is performed on the ChatGPT side.

Part III — Safety Boundaries and Division of Responsibility

12. Do Not Treat Sandbox as One Thing

Instead of asking “Is the Sandbox safe?”, consider what is allowed, and how far, at each boundary.

File boundary       what can be read / written
Execution boundary  what can be launched
Shell boundary      which commands are allowed
Network boundary    where communication is allowed
Secrets boundary    whether credentials and similar data are visible
Human-judgment boundary  where work returns for Approval

Do not judge safety from the Sandbox mode name alone; verify the actual boundaries for reading, writing, execution, and communication.

13. Separate Work Rules, Authority, and Execution Rules

Do not treat mechanisms with different roles as one unified safety mechanism.

Work rules          = what may be done
Sandbox / OS permissions = what is technically executable
Approval            = human judgment when crossing a boundary
Execution rules     = classification of execution requests

Written rules, technical authority, human confirmation, and classification of execution requests each carry different responsibilities.

In the current product, mechanisms such as AGENTS.md, config, and .rules may implement these roles, but their concrete names and behavior can change.

Deciding in documentation that something “must not be executed” is different from making it technically impossible to execute. Written rules alone cannot completely prevent execution caused by mistaken judgment or mistaken operation.

If the entire PC is readable, Codex may be able to reach private documents or confidential information unrelated to the work target. Because unintended access or transmission cannot be completely prevented under such authority, this must be treated as an explicit privacy risk.

14. Separate “Can,” “Safe,” and “May”

can   = is it technically executable?
safe  = is the impact within an acceptable range?
may   = is it permitted as part of this job?
  • Sandbox / OS permissions = mainly can / safe
  • Execution rules / Approval = execution and authorization when crossing boundaries
  • AGENTS.md = mainly may

Do not assume that something is unrestricted because it is safe, or that having technical authority means the job permits it.

15. Think About Authority by Impact, Not Operation Name

The same command can have very different impact depending on its arguments and purpose. Think about authority not by command name, but by what it changes and how far the effect reaches.

Read-only                                      → normally automatic
Create/modify regenerable outputs              → normally automatic
Modify existing source                         → conditional
Modify/delete difficult-to-recover data        → confirm
External transmission / network                → confirm or prohibit
Write to the analysis target itself            → prohibit

Open only the capabilities that are needed. At the same time, avoid over-restricting the environment so finely that Approval appears constantly.

16. Approval Is a Division of Responsibility, Not “Distrust”

More Approval does not necessarily mean more safety. When confirmations occur too often, clicking becomes habitual, the human begins skipping or trivializing review, and even genuinely important confirmations stop being read carefully.

Safe routine work                     → no Approval
Boundary operation outside the norm  → Approval
Dangerous / external / hard-to-recover operation → Approval or prohibit

One reason to reduce Approval is to make sure the remaining Approval prompts are actually read by the human.

Known routine work should be permitted at an appropriate granularity after the real environment has been checked. Unknown executables, network connections, and access outside the work scope should be treated as separate responsibility boundaries.

17. Treat localhost / MCP as Separate Boundaries Too

127.0.0.1 is not outside the PC, but from Codex's point of view it is still network access and therefore distinct from the file boundary.

MCP can be used as a mechanism for connecting external tools and data in structured form. When using it, separate the following steps.

Register an MCP server
        ↓
Connect to the server
        ↓
Use the exposed tools

Do not treat the mere availability of MCP as a basis for concluding that it is safe. Inspect what the actually exposed tools can read, modify, and execute.

Treat read capabilities and change/execute capabilities as separate responsibility boundaries.

Availability and always-on loading are different questions. Capabilities with persistent cost, such as MCP or a browser, should be enabled only for work that needs them.

18. Verify Images, Audio, and Text Without Showing Their Contents

Do not bring the contents of images, audio, or text themselves into the model input.

  • Do not send the content itself to chat or external services.
  • Verify through headers, size, hashes, diffs, decode success/failure, and similar structural signals.
  • When content inspection is necessary, the human should check it locally on the PC.

Also account for the possibility that sensitive content may appear accidentally.

If equality with the original data or structural information is sufficient for verification, there is no need to ask the AI to judge the contents.

19. Do Not Identify the Original Work

In the local analysis described in this document, the target may contain data from a commercial or creative work.

Even when the title is not explicitly provided, strings inside an EXE, filenames, copyright notices, resource names, and similar clues may reveal the work's identity.

  • Do not search strings or the web for the purpose of identifying the work.
  • If a title or manufacturer name is discovered incidentally, do not record or report it unless it is necessary for the analysis.
  • Do not use the title of the work as an assumption for file-format or algorithm analysis.

Make the rule “do not identify the work,” not merely “do not tell the Agent the title.”

20. Treat External Search as External Transmission

The moment a distinctive string is used for a web search, that information has left the local PC.

Do not send analysis information to external search or the network.

Prevent Information from Leaving

  • Close the network for analysis that does not require it.
  • Set execution boundaries in Sandbox / config as well as in policy.
  • If external investigation is necessary, separate it from local analysis.

Also Be Careful About Information Coming In

Web pages, search results, and external documents can incorrectly steer Codex's next actions.

Closing the network therefore serves not only to prevent information from being sent out, but also to reduce hostile or misleading input coming from outside.

Part IV — Execution Environment and Capability Selection

21. Preserve the Build Environment as Shared Knowledge

Do not expect Codex in a new project to automatically know a build environment that was verified in a previous project.

Assumptions about which existing environment to use, such as MSYS2 and the chosen GCC / make, should be preserved in AGENTS.md.

  • Use the specified existing environment.
  • Do not perform unnecessary toolchain discovery or installation.
  • Do not modify or update the build environment without permission.

By contrast, the concrete procedure for invoking that environment and building with it belongs in OPERATIONS.md.

AGENTS.md
  which build environment to use
  what may be changed

OPERATIONS.md
  how to invoke that environment
  what build and verification procedure to follow

Do not mix assumptions about the environment itself with concrete work procedures.

22. Measure Sandbox / Approval with a Probe

When the effective boundary cannot be determined from UI or configuration alone, use a small boundary-checking test (called a Probe below) to measure the real boundary.

The ability to execute an existing GCC is a different boundary from what its child processes or generated EXE files can access.

Check the boundaries required by the work, including read, write, execution, network, and Approval. Do not use real data. The Probe should do nothing beyond measuring boundaries: no configuration changes, circumvention, or automatic repair.

Do Not Let Codex Judge the Result by Itself

  • Human: checks whether an Approval dialog appeared.
  • Probe: records success or rejection of each operation.
  • Codex: organizes and reports the result.

Do not judge Sandbox safety from configuration text alone; measure and confirm the actual boundary.

23. Use Rejection to Map the Effective Specification

A rejection is not merely a wall that stops work; it is an observation that allows the Agent to revise its next action.

For example, if Sandbox, lint, test, or build rejects an operation, the result is not merely “execution failed.” It also tells us that this path or state does not hold in the current effective environment.

An attempt is rejected
        ↓
Observe the fact and reason for rejection
        ↓
Revise the current hypothesis or path
        ↓
Retry through a different path
        ↓
Continue the work

A rejection loop that returns useful information is feedback that teaches the Agent the shape of its autonomous search space.

24. Provide the Necessary Tools, While Keeping Privilege Narrow

If the human avoids the effort of preparation and fails to provide the AI with the tools, source material, and observation methods it needs, speculation and detours increase, which can actually reduce both quality and safety.

Choose first the path that can achieve the objective with the fewest dependencies and the narrowest privileges.

Withholding unnecessarily powerful means is different from withholding necessary means.

Least privilege does not mean minimal tooling.

Part V — Analysis and Verification

25. When Something Fails, Return to Primary Sources Before Generating Many Alternatives

When analysis or reimplementation does not match expected results, continuing to change only the implementation will preserve the same mistake if the underlying assumption is wrong.

Expected value and measured value disagree
↓
Identify the first observable divergence
↓
Identify the relevant process / command
↓
Return to ASM / binary / primary source
↓
Recheck assumptions
↓
Fix implementation
↓
Verify again

If repeated attempts under the same hypothesis do not improve the result, stop making local patches and return to the assumptions.

26. Move from Low-Level Observation to High-Level Explanation

If structural analysis keeps accumulating only low-level information without progressing to a higher-level explanation, that is a sign that the analysis has stalled.

Statistics, diffs, and observations from multiple analysis tools are means for discovering structure. From there, move to the code that creates or uses the data, ASM, and runtime behavior, until reaching a point where you can explain why the structure has that form.

Cycling through the same data with different analysis tools merely accumulates more low-level observations if it does not lead to a higher-level explanation.

If no basis for moving to a higher-level explanation can be found, do not keep stacking the same investigation. Stop there and return the work to the human.

Judge analytical progress not by the amount of information collected, but by whether observation has advanced into explanation.

27. Do Not Use AI-Generated Artifacts as the AI's Own Ground Truth

Do not compare several AI-generated alternatives and declare one correct merely because “this one looks more plausible.”

Use observations that are as independent as possible from the generated artifact for correctness judgment.

  • Measured behavior of the original EXE
  • ASM / binary diff / comparison of runtime state
  • harness (verification execution/comparison environment) / state-transition logs
  • Known file structures
  • Hash equality

Do not close correctness judgment inside the AI itself; place it outside the generated artifact.

28. Humans Can Be Wrong Too

Do not treat all information supplied by the human as confirmed fact.

In particular, separate facts that were actually observed from guesses about their cause.

“The color looks wrong”       = observation
“The palette is the cause”    = hypothesis

When a likely cause is strongly suggested, Codex may treat it as established fact and proceed deeply in the wrong direction.

Therefore:

  • Treat proposed causes as hypotheses until verified.
  • Record observations separately from causal guesses.
  • Do not preserve hypotheses that contradict measurements or primary sources.
  • If a supplied assumption contains or creates a contradiction, return that contradiction.

Even when the human holds final responsibility, the human's guesses do not thereby become correct.

29. Do Not Treat Skipping as Analysis Completion

Even when the textual content inside a script does not need to be understood, simply skipping it may not be sufficient.

To follow commands correctly, the text regions and command arguments still need enough structural processing to determine the position of the next instruction.

  • Control commands, opcodes, arguments
  • Branches, jumps, flag operations
  • Lengths, termination conditions, and boundaries needed to determine the next instruction position
  • The skipped range and the basis for skipping it

Do not conclude that analysis is correct merely because content could be skipped or execution reached the end.

30. “It Ran to the End” Does Not Mean It Was Correct

Even if all data can be processed to completion, the analysis may still be wrong.

For example, a drawing variable might be mistaken for an internal script variable, yet processing could still reach the end as long as reads and writes remain structurally valid.

Successful completion is not evidence that the meaning of commands or variables has been understood correctly.

Structural Verification

If the goal is to enumerate control commands correctly, verify the following against a large amount of real data.

  • Zero unknown opcodes
  • Zero out-of-range reads
  • Zero broken command lengths
  • Reached end-of-file for every file

Semantic Verification

When necessary, record the opcode, arguments, and before/after execution state for each command.

Verify normal cases broadly, then investigate narrowly and deeply where anomalies appear.

31. The Granularity of Observation Constrains Understanding

Computer processing is often understood as a correspondence between input and output.

Input
 ↓
Processing
 ↓
Output

This view tends to remain at the dimension of whether the output result is correct.

For example, if a single chat exchange contains N characters, the human and the Agent understand one another only through the slice of state exposed by those N characters.

The length of that text and the way it is segmented define the world they can mutually understand.

Even when observing through a highly capable system, do not mistake what is visible for the whole world.

Part VI — Stop, Return, and Self-Recovery

32. Limit Autonomy to Closed Work Loops

Autonomy does not exist merely because a document says, “You may decide for yourself and continue.”

For the work in question, there must be a loop in which the Agent can:

  • observe state,
  • verify results,
  • recognize failure,
  • recover within a defined range, and
  • return to the human when necessary.

Such a work loop must actually be in place.

If any of these is missing, widening authority merely extends discretion into a range where judgment cannot be grounded.

The ceiling of autonomy is determined not by AI capability, but by the range in which this work loop can be closed.

33. Do Not Define “Return = Failure”

Without explicit stopping conditions, Codex tends to continue working under the belief that “there is still something else to try.”

If return is treated as lack of capability, Codex is pushed toward forced completion:

I don't know
↓
There is still something to try
↓
Fill the gap with speculation
↓
Continue using that hypothesis as an assumption
↓
“Completed”

This pattern becomes more likely.

Therefore, define correctly detecting insufficient evidence and returning to the human as a form of success.

Criteria for Stop, Consultation, and Return

In the following cases, stop the work and report confirmed facts, unresolved items, what was tried, and what should be checked next.

  • Multiple interpretations remain viable and cannot be ranked.
  • Repeated attempts based on the same hypothesis do not improve the result.
  • Measured results contradict the current hypothesis.
  • Correctness begins to depend on a guess that merely “seems plausible.”
  • Continuing requires a user decision or new verification data.

Prefer making uncertainty explicit and returning the decision to the human over forcing completion without sufficient basis.

34. Humans Also Have a Responsibility to Stop

When the human can no longer judge whether the result is valid, stop Codex and verify.

If discomfort or doubt has been noticed, do not pretend not to see it or ignore it for convenience.

Stopping is not only Codex's responsibility; the human has a responsibility to stop the work as well.

35. Do Not Interpret Dissatisfaction with Return as a Demand for Forced Completion

A human being dissatisfied with a return is not the same as asking for forced completion.

If the quality of the return is poor, improve the way the work is returned rather than eliminating return itself.

Poor Forms of Return

  • Returning too early
  • Leaving obvious avenues of investigation unused
  • Asking again for information that has already been provided
  • Dumping unorganized material onto the human
  • Failing to explain why the work is being returned

A Good Return Should Show

  • Confirmed facts
  • Unresolved items
  • Verification already performed
  • Why continuation is not currently justified
  • What should be checked next
  • Points requiring human judgment

There is value in recording “I don't know” correctly.

36. Define the Scope of Self-Recovery in Advance

If every failure immediately returns to the human, work becomes fragmented.

Therefore, separate in advance the range where self-recovery is safe from the boundary where the work must return to the human.

The criterion for continuing self-recovery should be progress, not retry count. If no new information, hypothesis update, or state change is occurring and the same actions are being repeated, treat that as failure of self-recovery.

Self-recovery should occur only within a pre-defined range.

Part VII — Long-Running Operation and Handoff

37. Measure First When the Scale of an Operation Is Unknown

Even reading and searching consume CPU, I/O, time, and context.

For searches, enumeration, or scans whose scope or cost is unknown, first check item count, data size, search range, or similar measures when possible. There is no need to estimate ordinary small operations whose scope is already obvious.

“It does not change state” and “it can be canceled” are not reasons to ignore execution cost.

38. Externalize State for Long-Running Work

For long-running work, do not use conversation context as the only place where work state is preserved.

Leave hypotheses, their supporting basis, and unresolved items in memo/<tool>_analysis.md, and confirmed facts in memo/<tool>_spec.md, so that the next session can reconstruct work state from files.

Even as history and artifacts grow, do not let the state required for control and resumption grow in proportion. Preserve full history in external memory, and bring only summaries and references into the current work.

39. Verify State Transitions in Long-Running Work

In long-running processes, checking only immediately after start and at final completion makes it easy to miss state transitions that occur in between.

Authentication refresh, reconnection, date changes, rotation, context compression, and growth in accumulated data can make the transition point itself a failure boundary.

Confirm normal state at start
      ↓
Intermediate state transition
      ↓
Confirm normal state after transition
      ↓
Confirm final result

If an intermediate boundary can be extracted as an independent work unit, consider separating work or verification at that point. The fact that an intermediate check is necessary can itself be a sign that the work can be divided into separate units.

However, if the state transition belongs inside one minimum work unit and splitting it would destroy the thing being verified, do not divide the process artificially. Place observation and verification points inside the minimum work unit, and confirm that correctness holds across the transition.

Separate boundaries that can be separated. For boundaries that lose meaning when separated, put observation points inside them.

Confirm that the conditions under which the work remains valid are preserved across state transitions caused by time.

40. Separate the Time Direction from the Work Direction

Even a measured value cannot be attributed to the current work if another work process, cache, temporary state, or load is mixed into it.

Traditionally, isolation was viewed mainly as a way to:

  • avoid breaking other work,
  • avoid damaging originals, and
  • avoid exceeding authority,

that is, as a mechanism for containing effects.

But isolation has another role.

Isolation
├─ contain effects
└─ preserve evidence attribution

The latter is a boundary that protects:

what may legitimately be trusted as evidence.

For an Agent to reason correctly, access to information is not enough. It must also be possible to identify which state, which work unit, and which change produced that information.

To separate evidence, separate the worlds that produce the evidence.

Work A ─ File A ─ Runtime state A ─ Observation A

Work B ─ File B ─ Runtime state B ─ Observation B

In the time direction, separate state transitions.
In the work direction, separate the worlds themselves.

If independent measured values are required, make the observed worlds independent as well.

41. Preserve Snapshots by Date

In analysis work, intermediate artifacts and regenerable data can become large. There is no need to put everything under Git.

In the current operational example, work/ is divided by date, with the state of each day's work collected under work/MMDD/.

work/
  MMDD/
    tmp/          # temporary area for GCC and similar tools
    generator-a/  # example name of a generated tool
    generator-b/
    ...

work/MMDD/ is treated as a snapshot containing that day's implementation, experiments, and generated artifacts.

Artifact folders under work/MMDD/ are named primarily after the generated tool, rather than by broad purpose.

tmp/ is a temporary area used by GCC, MSYS2, and other tools. Keep temporary files inside that day's work/MMDD/ whenever possible.

When the date changes, artifacts required for continuing work may be duplicated across multiple work/MMDD/ folders. Treat folders from previous dates as snapshots and perform new work in the current day's work/MMDD/.

Rather than forcing large regenerable data into Git history, prioritize being able to reconstruct that day's work state from work/MMDD/.

42. Perform Both End-of-Work Cleanup and Human Retrospective

When work ends, Codex should first follow OPERATIONS.md and return after leaving a state from which the next session can resume.

The desk may become messy during work. Do not hand the next session a messy desk.

End-of-work cleanup and human retrospective are separate processes.

The human reviews not only the result, but also the way the work was performed and the operation itself.

The retrospective is initiated voluntarily by the human.

If only failures are used as improvement material, operating rules tend to accumulate rather than be removed. By also examining why things worked well, it becomes possible to decide which mechanisms should remain and which are unnecessary.

If an operations document needs to change, that change is made through the ChatGPT-side maintenance path.

Part VIII — Evolving the Operation

43. Classify Failure Before Changing the Operation

When Codex fails, do not immediately add rules or reduce its discretion.

First check whether Codex could actually use the information, tools, observation, verification, and recovery mechanisms required for the work.

Examples:

  • It could not reach required information.
  • It could not use a required tool.
  • It could not observe the result.
  • It could not independently verify correctness.
  • It could not recover from interruption or failure.

If something is missing, begin by supplying it.

Do not mistake a deficiency in the Harness for a deficiency in rules.

Then, if recurrence prevention is still necessary, identify what actually needed to be protected before adding prohibitions.

44. Choose Between “Guide with Information” and “Enforce with Mechanism”

There are at least two directions for solving the same operational problem.

Guide with information

Use Markdown and information structure so the AI can reference the necessary information, principles, and choices while preserving judgment appropriate to the situation.

Examples:

  • Put assumptions needed for judgment in AGENTS.md.
  • Put repeatable procedures in OPERATIONS.md.
  • Structure directories and documents so required information is easy to discover.
  • Make state and verification results observable to the AI.

Enforce with mechanism

Use technical mechanisms so incorrect results or disallowed operations can be detected and rejected without relying on AI judgment.

Examples:

  • test
  • Sandbox
  • fixed input/output boundaries
  • designs that structurally make invalid operations impossible

Enforcing with mechanism is not only for safety.

It reduces the range that the AI must judge every time.

45. If the Same Judgment Is Repeated Every Time, Ask Whether It Can Move into the Environment

Do not make “giving the AI freedom” a goal in itself.

The following kinds of judgment are candidates for enforcement by mechanism.

  • Conditions are almost fixed.
  • The same conclusion is reached nearly every time.
  • The decision can be made mechanically.
  • The decision can be made mechanically and the cost of a mistake is large.
  • The same materials are reread every time to make the same judgment.

By contrast, guiding with information is usually better when:

  • the correct answer changes by situation,
  • primary sources must be interpreted,
  • human intent or purpose is part of the judgment,
  • unknown exceptions must remain possible, or
  • conditions are likely to change in the future.

Do not enforce merely because enforcement is possible. Enforce when doing so removes reasoning that does not need to be repeated.

46. Adapt Operations to the Environment, and Let Design Learn from Operations

Models, Sandbox, Approval, MCP, Skills, and other parts of the execution environment change. Therefore, do not treat settings and operating procedures that work well today as permanent assets in their current form.

In particular, model-specific workaround instructions, product/UI/tool-specific procedures, and prompt tuning should be treated as short-lived artifacts adapted to the current environment.

By contrast, design reasons such as the following are more likely to survive implementation changes.

Why was this boundary necessary?
What kind of incident was it meant to prevent?
What should be returned to the human?
Which responsibility was placed in which layer?

The current AGENTS / OPERATIONS / Skills / config are closer to build artifacts for the current environment.

Design philosophy and reasons
      ↓
      ↓ distill
Current operating setup
      ↓
      ↓ use in practice
successes / failures / discomfort / measurements
      ↓
      ↓ retrospective
feed back into design philosophy and reasons

When the model or product changes, do not carry the old operation over unchanged. Return to the design reasons and reevaluate whether each mechanism is still necessary.

Lessons from incidents, discomfort, unnecessary constraints, and mechanisms that worked well in practice should be returned to the design when they can be reused across environments.

Rules are things to follow, but when they are observed to conflict with reality, they also become objects of inspection.

Adapt operations to the environment, and let design learn from operations.

47. Do Not Use Conversation as the Memory of the Work

In human work, ambiguous exchanges in speech and chat have often been filled in by shared experience and common knowledge.

Information such as “what we discussed before,” “the feel of yesterday's work,” or “the exception that applies only here” may be sufficient in the moment, but disappears as time passes or the person responsible changes.

Bringing Agents into work makes this weakness more visible.

Conversation is where judgments are produced; it is not where judgments should be preserved.

For example, do not leave feedback obtained from Codex trapped inside chat. Use ChatGPT to organize intent, constraints, changes, and reasons.

Move the resulting judgments into forms that can be referenced later—design, specifications, operating procedures, verification conditions, and so on—and return the necessary pieces to Codex.

A judgment produced in conversation becomes work memory only after it is moved outside the conversation.

48. Codex Will Break Things

Codex can cause serious incidents: selecting the wrong target file, overwriting the wrong file, or damaging a project through an operational mistake.

These are not exceptional accidents. They occur with some probability because modern agents do not necessarily produce the same judgment or command every time, even when given the same textual instruction. Unfortunately, this can happen even in ways that slip past instructions and prohibitions explicitly written in AGENTS.md.

Tracing exactly why it broke may often be wasted effort.

Build an environment in which Codex can break without breaking the work.

49. What Is a Harness?

A Harness is not merely a collection of rules for assigning work to AI.

It is an environment assembled from the necessary information, authority, observation, verification, rejection, recovery, and return paths so that work can proceed without requiring a human judgment at every step.

Its purpose is not to make AI autonomous without limit.
Its purpose is to concentrate scarce human judgment at the places that genuinely require human judgment.

Good Job

What counts as good in this work?

A specification for the artifact alone does not determine the direction of the work.

In addition to explicit requirements, work contains judgments that determine which way to proceed.

taste, risk tolerance, polish, shortcut, done. Aesthetic judgment, how much risk to accept, how much refinement to pursue, what may be omitted, and where to stop.

These cannot each be replaced with one fixed condition.
They give a common direction to many small judgments and shape what counts as a Good Job for that work.

Good Job does not designate one exact point corresponding to a finished artifact.

Among multiple viable choices, which is better?
How much risk should be accepted?
How much polish is enough?
What may be omitted?
Where should the work stop?

Good Job gives direction to judgment.

Without direction, locally correct improvements can continue without limit.

More tests, stronger abstraction, stricter review, and more explanation can each appear correct in isolation.

But if the direction of the work is not defined, stacking correct improvements does not guarantee convergence.

Good Job is not a vague human feeling outside the Harness.
It is a design object that gives direction to the Harness as a whole.

Judgments That Remain with the Human

At minimum, the following judgments remain on the human side.

  • What counts as a Good Job?
    Decide which direction the work should take.
    taste, risk tolerance, polish, shortcut, and done make up this direction.

  • What are the invariants?
    Decide what must always remain true even while moving in that direction.

  • What counts as evidence?
    Decide what must be observed in order to verify the invariants and required properties.

  • Is the evidence sufficient?
    Decide whether the observed evidence is enough to accept the result as sufficiently established and stop here.

The work of collecting evidence itself can be moved to AI and the environment wherever possible.

Through inspection, logs, comparison, tests, measurement, rejection, and retry, AI can perform the work, observe failure, correct it, and gather evidence on its own.

Therefore, the human does not need to supervise every step of the process.

Good Job
“What direction should this work move in?”
        ↓
Invariants
“What must never be crossed?”
        ↓
Evidence
“What must be observed to verify it?”
        ↓
AI executes
        ↓
The environment observes and rejects
        ↓
AI corrects the work and gathers evidence
        ↓
Sufficiency
“Given this evidence, can we believe the work holds
 and stop here?”

Invariants define boundaries.
Evidence shows where the work currently stands.
Sufficiency decides when to stop.

Before all of them, Good Job gives the direction in which the work should move.

Where to Leave Human Judgment

As the Harness improves, the human role moves away from execution.

From giving detailed instructions about what to do,
to defining what good work means.

From supervising the work,
to deciding what must be protected and what observations justify trust.

From continuing improvement indefinitely,
to deciding which evidence is sufficient to stop.

A Harness is a mechanism that concentrates scarce human judgment into Good Job, invariants, evidence, and the sufficiency of that evidence.

Conclusion

The goal is not to keep issuing detailed instructions to Codex every time.

The goal is to make the underlying environment, authority, rules, external memory, verification, recovery, and return paths so well prepared that a job can be delegated in a single sentence.

Do not keep piling up detailed instructions around Codex. Grow a workplace in which Codex can work without losing its way.

If a problem occurs but the existing procedures recover correctly, do not add rules unnecessarily.

And humans should not try to keep everything in their heads either.

Do not optimize for never forgetting. Build a system that lets you recover even after forgetting.

Start small so that building the workplace does not overwhelm the actual analysis work, and improve only where real operational feedback appears.
