対象から概念を発見するための観測法

目的: 対象を既存の名前や分類として受け取るのではなく、そこに現れる状態、差、関係、作用、境界から、議論可能な Concept の輪郭を発見する。

本書は特定の対象の読み順や調査手順を定めるものではない。Concept をあらかじめ定義して対象へ当てはめるのではなく、複数の観測から輪郭を取り、その輪郭が何を表しているかを発見するための視点を整理する。

Concept は、条件を何個満たしたかで認定するものではない。

世界は動き続け、観測者も固定されない。Concept は世界そのものの state を保存するものでも、発見した時点で正しさを保証されたものでもない。

一方で、任意に線を引いて Concept と呼ぶわけでもない。観測できる差、反復、境界、作用、評価が議題として残るとき、その輪郭を候補として扱う。

対象をどこから見るかによって、同じものが部分にも全体にもなり、同じ遷移が継続にも断絶にも見える。

そのため、本書では一つの絶対的な輪郭を先に置かない。

failure
state
lifecycle
identity
dependency
composition
transition
authority
scope
observation
criterion

複数の軸から対象を切り、そのたびに現れる境界を重ねる。

そこで繰り返し残る責任、状態、関係、禁止、遷移、基準が、Concept の候補になる。

Concept Discovery は、名前を付ける作業ではない。動き続ける世界から、議論できる輪郭を持ち帰る作業である。

第I部　輪郭を発見する

1. Concept は定義する前に輪郭を取る

調査の最初から、対象を既知の分類へ入れようとしない。

最初に得られるのは、断片的な finding である。

ここで state を保持している
ここで retry を止めている
ここで authority を確認している
ここで別の経路へ分かれる

一つ一つは事実であっても、それだけでは Concept ではない。

複数の finding が、同じ責任や境界を別の場所から指し始めたとき、一つの輪郭が見える。

finding
finding
finding
   ↓
同じ境界を指す
   ↓
Concept の輪郭

ここで重要なのは、先に名称を決めないことである。

名称は輪郭を見やすくするために使うのであって、輪郭を名称へ合わせるために使わない。

断片を集めるのではなく、断片の背後で繰り返し現れる輪郭を探す。

2. 観測位置を固定する

同じ対象でも、見る位置によって輪郭は変わる。

たとえば Task は、

人間から見る      一つの仕事
Loopから見る      Goalまでの区間
engineから見る    遷移する state unit
保存層から見る    復元対象

として現れることがある。

どれか一つを唯一の正しい Task と決める必要はない。

先に決めるのは、どの関係、どの責任、どの状態遷移から見ているかである。

観測位置を固定すると、その位置から見える輪郭を議論できる。

さらに、別の位置から得た輪郭と並べると、ずれそのものが設計上の問いになる。

人間には一つに見える
engineでは二つに分かれている

この差は説明の違いではなく、責任や状態の境界が一致していない可能性を示す。

Concept の輪郭を語る前に、どこから見た輪郭なのかを固定する。

3. 機能名ではなく責任を読む

対象には、製品固有の名前が多く現れる。

workflow、facet、reviewer、task のような名前を覚えても、それだけでは他の設計へ持ち出せない。

見るのは、その機能が何を担当しているかである。

何を保持するか
誰が読むか
いつ生成されるか
どこへ保存されるか
次へ何を渡すか
何が状態を変えるか

別の機能にも同じ責任が現れるなら、その責任は製品固有機能より上位の Concept である可能性が高い。

反対に、同じ名前でも責任が異なるなら、同じ Concept とみなす理由は弱い。

対象は名前の集合ではなく、責任の配置として読む。

4. 正常系より失われる瞬間を見る

成功経路では、多くの状態が暗黙のままでも動く。

境界が露出するのは、失敗したときである。

retry
resume
requeue
timeout
abort
conflict
stale
missing
exceeded

このような経路を読むと、

  • 何を識別し直す必要があるか
  • 何が正本でなければならないか
  • 何を二重実行してはいけないか
  • 何を最後の正常状態として残すか

が見える。

failure は Concept を壊すだけではない。

普段は隠れている責任や境界を、観測可能な形にする。

成功経路より、再開経路の方が設計思想をよく表す。

5. 成立させない状態を見る

設計は、何を実行するかだけでなく、何を成立させないかにも現れる。

二重実行させない
stale actor に書かせない
未検証 state を正本にしない
権限外へ出さない
不完全な結果で次へ進ませない

そのために、実装には次のような道具が現れる。

guard
validation
version
lease
fence
assert
reject

道具そのものを一般化する必要はない。

複数の場所で同じ禁止状態を守っているなら、その禁止の背後に invariant がある。

failure path が「壊れたときに何が露出するか」を見るのに対し、invariant は「そもそも何を壊れた状態として成立させないか」を見る。

存在する機能だけでなく、成立を拒まれている状態から Concept を掘る。

6. 見えるものと見えないものを分ける

Concept のすべての性質が、同じ場所から観測できるとは限らない。

UIでは active
runtimeでは terminated

外からは成功
内部では durable state が未確定

logには残る
canonical stateには残らない

ここで見るのは、単なる observability の量ではない。

どの性質がどの観測面から見え、その欠落がどの誤認を生むかを見る。

たとえば「完了」は UI 表示だけでは確定できないかもしれない。

「権限がある」は設定値だけでは確定できないかもしれない。

観測できるものだけで Concept を定義すると、見えない部分を存在しないものとして扱ってしまう。

何を認知でき、何を認知できないかも、Concept の輪郭の一部である。

7. 「ない」を一つにしない

何かが見つからなかったとき、すぐに存在しないと結論しない。

たとえば checkpoint がない には、複数の状態がある。

そもそも存在しない
存在するが、このAPIから見えない
存在するが、現在のactorには読めない
存在するが、まだmaterializeされていない
存在したが、失効した
観測手段そのものがない

同じことは、state、authority、history、evidence にも起こる。

nonexistent
unknown
inaccessible
hidden
expired
not yet created

これらを一つの「ない」に畳むと、Concept の境界を誤る。

不在を観測するときも、観測位置と観測可能性を先に固定する。

見えないことと、存在しないことを同じ finding にしない。

第II部　状態と時間を追う

8. ファイルではなく状態を追う

一つのファイルを最初から最後まで読んでも、設計上の責任が見えるとは限らない。

状態は複数の場所を通る。

schema
  ↓
loader / builder
  ↓
runtime
  ↓
persistence
  ↓
resume / failure
  ↓
test

たとえば一つの Task state が、schema で定義され、runtime で更新され、別ファイルへ保存され、resume で再利用されるなら、その一連を一本として読む。

同じ state を追うことで、実装ファイルをまたいで一つの責任が見える。

Concept はファイル境界ではなく、状態が通る経路に現れる。

9. lifecycle を時間軸として読む

state がどこに存在するかだけでなく、時間とともにどの状態を通るかを見る。

create
  ↓
active
  ↓
suspend
  ↓
resume
  ↓
complete
  ↓
retire

これは別々の Concept を並べているのではない。

一つの Concept が時間軸上で持つ輪郭を追っている。

各遷移について、

  • いつ存在し始めるか
  • いつ意味や authority を持つか
  • 何をきっかけに無効になるか
  • suspend 中に何が保持されるか
  • 終了後に何が残るか

を見る。

時間方向の遷移を一本で追うと、単一時点の state だけでは見えない境界が現れる。

Concept の輪郭は、ある時点の値だけでなく、時間軸上の遷移にも現れる。

10. 遷移を通して残る芯を見る

同じ Concept は、時間の中で多くのものを変える。

Task なら、仮説、実装、担当、作業方法、検証手段が途中で変わることがある。

それでも「同じ Task を続けている」と扱われることがある。

開始
  ↓
調査
  ↓
実装
  ↓
失敗
  ↓
再定義
  ↓
再開

ここで見るのは、不変の部品を探すことではない。

何が変わっても同じものとして扱われ、何が変わると別のものとして扱われるかを見る。

実装上は、次のようなものが同一性を支えることがある。

identity
operation id
generation
version
owner
parent
checkpoint

しかし識別子が同じだから同じ Concept とは限らない。

逆に、構成要素が置き換わっても、設計上は同じものとして追跡されることがある。

テセウスの船を解く必要はない。

見るのは、その設計が何を同一性の規則として採用しているかである。

遷移の中で残る芯を探し、何をもって同じものとしているかを読む。

11. 可逆と不可逆を分ける

時間軸上の遷移には、戻れるものと戻れないものがある。

draft → approved
open → closed
candidate → canonical
temporary → committed

見かけ上、以前の state に戻せても、世界全体が以前と同じになるとは限らない。

ファイルは戻せる
外部APIへ送った事実は戻らない

stateは戻せる
人間が見た情報は戻らない

設定は戻せる
一度成立した承認履歴は残る

そのため、次を分けて読む。

reversible state change
compensation
reconstruction
rollback
irreversible effect

rollback は、世界そのものの state 保存ではない。

どの境界を越えると以前と同じものではなくなるかを見ると、その Concept にとって意味のある変化が見える。

可逆性ではなく、何が戻らないかから遷移の重さを読む。

12. working context と durable state を分ける

Agent が今読んでいる context と、再開のために残す state は目的が違う。

working context
  今回の判断に使う

durable state
  session を跨いでも残す

event log
  何が起きたかを記録する

artifact
  作業の結果として残す

これらを一つにすると、再開時に大量の履歴を読み直したり、逆に必要な判断理由が失われたりする。

特に resume や retry がある実装では、どの state を再利用するのかを見る。

working context から durable state へ何を残すかは、単なる保存量ではない。

何を次の時点でも Concept の一部として必要とみなすかという判断である。

今必要な情報と、あとで復元するための情報を分けて読む。

13. 「本物」ではなく基準性を読む

同じ Concept が、複数の state や representation として現れることがある。

state → UI
state → cache
state → report
state → index

どれも Concept を表していてよい。

見るのは、表現が食い違ったときの非対称である。

どれを更新判断の基準にするか
どれから他を再構成するか
どれを失っても作り直せるか
競合したとき、どれを優先するか

canonical は、Concept そのものや絶対的な真実を意味しない。

その設計の中で、基準として扱われる役割を持つだけである。

どれが本物かではなく、どれが基準として扱われているかを読む。

14. 状態の置き場所と移動経路を分ける

情報が存在する場所と、それを次へ運ぶ仕組みは別である。

置き場所
  恒常環境
  Task固有層

移動経路
  Loop回覧経路

たとえば、Task固有の knowledge や policy が存在していても、次の cycle や別の担当へ渡されなければ、回覧経路は成立していない。

逆に、handoff の仕組みがあっても、何を正本として運ぶかが決まっていなければ、状態の再解釈が毎回発生する。

保存場所と transport を分けることで、Concept の保持責任と移動責任を別々に観測できる。

何を持つかと、どう運ぶかを同じ仕組みとして読まない。

第III部　関係から境界を読む

15. dependency から成立条件を読む

Concept は単独で成立しているとは限らない。

A があるから B が成立する
B がある間だけ C が有効
C を失うと D は意味を失う

ここで見るのは、依存関係一覧ではない。

その Concept が、何を失うと Concept として成立しなくなるかを見る。

たとえば、

approval
  depends on
request identity + current state + authority

resume
  depends on
checkpoint + environment + assumptions

となっているなら、依存物のどれが交換可能で、どれを失うと意味そのものが崩れるかを見る。

時間軸が「いつ同じものとして続くか」を示すなら、dependency 軸は「何に支えられて同じものとして成立するか」を示す。

外部条件を剥がし、どこで意味が崩れるかから Concept の輪郭を取る。

16. composition から部分と全体を読む

依存と構成は同じではない。

whole
 ├─ A
 ├─ B
 └─ C

A、B、C が互いに依存していなくても、一つの whole を構成していることがある。

ここでは、

  • 何を内部に含んでいるか
  • どの部分は交換可能か
  • どの部分を抜くと全体が成立しなくなるか
  • 一部が変わっても同じ whole と呼べるか

を見る。

重要なのは、部分と全体を絶対的な大きさとして扱わないことである。

同じ対象が、ある観測では whole であり、別の観測ではより大きな Concept の part になる。

Task は work の whole
Task は Loop の part

どちらも成立する。

部分と全体は観測位置で変わる。composition は、その視点から何が一つを構成しているかを見る。

17. authority は主体・対象・変化で読む

責任の所在と、変化を成立させる力は同じではない。

ownership
  誰が責任を持つか

authority
  誰が何に何を起こせるか

たとえば、request は作れても approval は別の主体しか成立させられないことがある。

state は読めても、基準となる state を更新できる主体は限られることがある。

主体だけを列挙しても authority は見えない。

誰が
何に
何を起こせるか

という関係を読む。

変化を成立させる主体・対象・効果の非対称から authority の輪郭を取る。

18. scope は効力の端から読む

composition が「何を内部に含むか」を見るのに対し、scope は「作用や規則がどこまで意味を持つか」を見る。

この Task にだけ有効
この Loop の間だけ有効
この session を越えない
この repository には効くが外部 system には届かない

ここで見るのは、単なる包含範囲ではない。

誰に
何に
どの条件で
どこまで効くか

が変わる地点を見る。

実在する作用に限らない。仮定上の規則でも、効力の条件と端を議論できるなら scope は観測できる。

何を含むかではなく、作用や規則の効き目がどこで終わるかを見る。

19. Concept と Concept の間を見る

Concept は、内部だけで完結するとは限らない。

二つの Concept の間を何が通るかに、独自の責任が現れることがある。

Maker
  ↓
artifact / diff / evidence
  ↓
Checker

あるいは、

working context
  ↓
selection / compression
  ↓
durable state

このとき、境界通過には、

  • 何を渡すか
  • 何を渡さないか
  • どの形式へ変換するか
  • 何を通過条件にするか
  • 誰が次の authority を持つか

という責任がある。

これは dependency でも composition でもない。

A と B の間で成立する handoff、conversion、promotion、rejection 自体に Concept がある可能性を読む。

Concept の内部だけでなく、Concept と Concept の間にも輪郭を探す。

20. 判定と状態変更を分けて読む

ある結果が出たことと、その結果に基づいて次の状態へ進むことは別である。

Observation
   ↓
Judgment
   ↓
State word
   ↓
Transition

実装では、この四つが一つの関数や一つの出力へ畳み込まれていることがある。

たとえば REJECT を見たときは、否定された事実だけでなく、

reason
retry condition
next route

がどこに保持されるかを見る。

Judgment が Concept を分類し、Transition が世界を変える。

この二つを分けると、観測と作用の境界が見える。

何を判定したかと、何を起こしたかを同じ責任にしない。

21. 推論と構造の境界を読む

Agent が意味を判断する部分と、engine や仕組みが固定する部分を分けて見る。

Inference
  意味を判断する
  候補を作る
  状況を解釈する

Structure
  state を保持する
  input を選ぶ
  transition を適用する
  Bound を強制する
  durable state を残す

重要な境界をすべて Agent の記憶や判断に任せているなら、その設計は推論側に寄っている。

逆に、すべてを構造で固定すると、状況依存の判断まで失う。

ここで見るのは、どちらが優れているかではない。

何を推論に残し、何を構造へ移したか、その境界にどんな責任が置かれているかを見る。

どの推論を構造へ移し、どの推論を残したかから設計思想を読む。

22. 一緒に変わる場所と分かれる場所から境界を読む

Concept は、変更の伝播にも現れる。

ある機能追加や修正で、

schema
runtime
persistence
resume
test
docs

が毎回セットで変わるなら、それらは同じ責任を共有している可能性が高い。

一方で、似た対象を並べたとき、扱いが分かれる地点にも境界が現れる。

A は保持する
B は捨てる

A は再開する
B は再生成する

A は人間が確定する
B は engine が確定する

Concept そのものを直接言葉にできなくても、どこで同じ扱いを受け、どこで分岐するかは観測できる。

co-change
  同じ責任の候補

divergence
  別の輪郭の候補

一緒に変わる場所と、似ているのに分かれる場所の両方から Concept 境界を読む。

第IV部　Concept として残す

23. 成立と「よさ」を分けて読む

成立することと、よいと判断されることは別である。

A でも動く
B でも動く

しかし A の方を選ぶ

その差には、明示された規則だけでなく、読みやすさ、対称性、単純さ、慣習、経験のような criterion が働くことがある。

一部は taste としか呼べない場合もある。

それでも、何を観測してその判断に至ったかを示せるなら、評価基準そのものを Concept の輪郭として読むことができる。

これは恣意性を認めることとは違う。

観測された差も関係もなく、乱数で線を引いただけなら Discovery ではない。

criterion は正しさを先に保証しないが、観測され、議論され、壊され、更新されうる。

何が成立するかだけでなく、何をよいとみなすかも観測する。

24. docs は地図、実装と test を一次資料にする

docs は、用語や入口を知るには強い。

しかし、docs に書かれた説明と、実際に状態を保持し遷移させている実装は同じとは限らない。

Concept の輪郭を確かめるときは、できるだけ次の順で確認する。

test / runtime artifact
        ↓
implementation
        ↓
schema / configuration
        ↓
official docs
        ↓
Issue / discussion

Issue は、Concept を定義する資料というより、境界が壊れたときに何が起きるかを見る資料として使う。

観測位置が違えば資料の価値も変わるが、Concept の成立を主張するときは、実際に守られている境界を優先する。

説明された設計より、実際に守られている境界を優先する。

25. 固有名を消しても残るかを見る

抽出した finding から製品固有語を消す。

facet
workflow
companion
repertoire

などを一般語へ置き換える。

それでも、

何を保持するか
何を運ぶか
何を判定するか
何を防ぐか
何に依存するか
何を同じものとして追うか

が説明できるなら、一般 Concept として残す価値がある。

固有名を消した瞬間に意味がなくなるなら、それは機能説明に近い。

ただし、一般化のために輪郭を削りすぎない。

名前を失っても残るのは、抽象語ではなく責任と境界である。

Concept は、名前を失っても輪郭が残る。

26. 既存モデルへ無理に押し込まない

先に持っている分類は、対象を読むための仮説であって結論ではない。

たとえば、

恒常環境
Task固有層
Loop回覧経路

という三つで多くを説明できても、すべてをそこへ押し込む必要はない。

次のような輪郭が繰り返し現れるなら、新しい Concept の候補として扱う。

独自の state を持つ
独自の lifecycle を持つ
独自の dependency を持つ
独自の authority や scope を持つ
別の観測位置からも同じ境界が出る
failure 時に独立して残る
他の Concept から単純に導出できない

これは判定表ではない。

複数の観測軸が同じ輪郭を指しているかを見るための手掛かりである。

分類を守るために例外を増やし始めたら、分類側を疑う。

対象をモデルへ合わせるのではなく、モデルを対象で壊す。

27. 追加読書が判断を変えなくなったら止める

対象を全部読む必要はない。

Concept Discovery の Goal は網羅ではなく、輪郭について判断可能になることである。

同じ責任について追加の実装や test を読んでも、

  • 分類が変わらない
  • state の境界が変わらない
  • lifecycle の理解が変わらない
  • dependency の理解が変わらない
  • authority や scope の理解が変わらない
  • criterion の理解が変わらない
  • failure の理解が変わらない
  • 新しい責任が出てこない

状態になったら、その探索の価値は下がる。

反対に、一つの failure path、一つの依存、一つの不可逆な遷移が既存モデルを崩したなら、そこは深く読む価値がある。

停止は「十分な量を読んだ」ではなく、「追加証拠が輪郭を変えるか」で決める。

読了はファイル数ではなく、追加証拠が Concept の輪郭を変えるかで決める。
