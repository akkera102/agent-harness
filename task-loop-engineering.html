Agentの仕事を、どう始め、続け、確かめ、止めるか

目的: Agent の仕事を、何によって始め、続け、確かめ、止めるかを整理する。Task と Loop の制御構造を扱い、特定製品の実装仕様とは分けて考える。

本書は特定の自律化方式を推奨するものではない。人間を Loop controller として残す場合も含め、仕事の開始・反復・終了条件を設計するためのガイドである。

第I部　Taskの基本構造

1. Taskとは何か

Task は、Agent に渡される仕事の単位である。

通常の対話では、人間が与える Prompt によって Task が始まる。

ただし、Task を起こすものは Prompt に限らない。時間、外部イベント、未達成状態なども Trigger になりうる。

Prompt / Time / Event / State
            ↓
           Task
            ↓
          Agent

つまり Task は Prompt そのものではなく、Prompt などの Trigger によって発生し、Agent が処理する仕事として捉える。

2. TriggerはTaskの開始条件を決める

Trigger は、何が起きたら Task を始めるかを決める開始条件である。

Trigger
   ↓
 Task
   ↓
 作業

通常の対話では、人間が与える Prompt が Trigger になる。

しかし、Trigger は Prompt に限らない。

  • 時間が来た
  • 外部イベントが発生した
  • 状態が変化した
  • Goal がまだ達成されていない

といった条件でも Task を始められる。

Prompt / Time / Event / State
            ↓
         Trigger
            ↓
           Task

重要なのは、Task が何をするかと、何がその Task を起こすかを分けて考えることである。

Trigger は Task の内容ではない。

Task の入口として、いつ仕事を始めるかを定める。

3. Taskには終了条件を与える

Task を与えるときは、何をするかだけでなく、何をもってその Task を終えるかを決める。

終了条件は、大きく次の3つの軸で考えられる。

Goal     到達したので終わる
Thought  判断できるので終わる
Bound    上限に達したので終わる

一つの Task が、一つの終了条件だけを持つとは限らない。

Task
 │
 ├─ Goal
 ├─ Thought
 ├─ Bound
 │
 ├─ Goal + Thought
 ├─ Goal + Bound
 ├─ Thought + Bound
 │
 └─ Goal + Thought + Bound

たとえば Goal を目指しながら Bound を上限にしたり、十分な根拠が得られた時点で Thought によって早く終了したりできる。

重要なのは、Agent に「まだ続けるか」を毎回その場で判断させるのではなく、Task 自体に終了を判断する軸を持たせることである。

4. GoalはTaskの到達状態を決める

Goal は、Task がどの状態になれば目指した状態に到達したとみなすかを示す。

Task
 ↓
作業
 ↓
Goal

たとえば、

  • 成果物が完成した
  • テストを通過した
  • 原因を特定した

といった、到達したかどうかを判断できる状態である。

Goal は「何をするか」という作業指示ではない。

Task の到達点として、何が成立すればよいかを定める。

5. ThoughtはTaskを考え続ける理由がなくなったら止める

Thought は、Task をさらに考え続けることで判断が変わる余地がなくなったら止める終了条件である。

Task
 ↓
調査・推論
 ↓
新しい判断材料が得られる
 ↓
さらに考える

この繰り返しを続け、

  • 十分な根拠が得られた
  • 仮説が必要な範囲まで絞れた
  • 次に確認すべきことが明確になった
  • これ以上考えても判断がほとんど変わらない

という状態になれば Task を終了できる。

Thought は、「Agent がもう十分考えたと感じた」という意味ではない。

さらに考えることで何が変わるのかを説明できなくなったとき、そこで止める。

Goal が Task の到達状態を定め、Bound が Task の許容範囲を定めるのに対して、Thought は 判断に必要な思考と根拠がどこまで揃えばよいかを定める。

6. BoundはTaskの許容範囲を決める

Bound は、Task をどこまで進めてよいかを決める境界である。

Task
 ↓
許容された範囲で進める
 ↓
Bound を越えない

Bound には、たとえば、

  • 時間
  • 試行回数
  • コスト
  • 変更範囲
  • リスク

などを置くことができる。

時間、試行回数、コストのような Bound は、上限に達したら Task を閉じる。

変更範囲やリスクのような Bound は、その境界を越えずに Task を進める。

調査や探索のように、途中までの結果にも価値がある仕事では、上限に達した時点で無理に Goal へ到達したことにはせず、その時点までに分かったことと、残っていることを返す。

ここでいう時間は、Task を再び起こす Trigger としての Time とは別である。

Bound は、Goal を目指す Task がどこまで進んでよいかを定める。

7. 終了条件は組み合わせられる

Goal、Thought、Bound は、一つだけで使うとは限らない。

Task の性質に応じて組み合わせられる。

組み合わせ 終了の考え方
Goal + Thought Goal を目指すが、十分な判断材料が揃えば止める
Goal + Bound Goal を目指すが、Bound に達したら止める
Thought + Bound 十分な判断材料が揃えば止め、揃わなくても Bound で止める
Goal + Thought + Bound Goal、Thought、Bound のいずれかが成立したら止める

たとえば Goal + Thought + Bound なら、

Task
 ↓
Goal を目指す
 ↓
├─ Goal 達成     → 終了
├─ Thought 成立 → 終了
└─ Bound 到達   → 終了

となる。

三つの終了は、同じ意味ではない。

Goal     到達したので終わる
Thought  判断できるので終わる
Bound    上限に達したので終わる

Thought や Bound で終了した場合、Goal は未達成のことがある。

その場合は、Goal を達成したことにはせず、現在地、分かったこと、不足しているものを残して Task を閉じる。

Task が終了したことと、Goal を達成したことは同じではない。

8. Taskの入口と出口を分ける

Task は、何が起こすかという入口と、何が止めるかという出口に分けて考えられる。

Human / Time / Event / State
            ↓
          Trigger
            ↓
           Task
            ↓
    Goal / Thought / Bound

入口側では、何が Task を起こすかを見る。

出口側では、何が Task を止めるかを見る。

時間は、入口では Trigger として使われ、出口では Bound として使われる。

入口の Time   時間が来たので始める
出口の Bound  時間上限に達したので終える

入口と出口は独立して組み合わせられる。

入口と出口の組み合わせによって、Task の輪郭が決まる。

第II部　Loop の基本構造

9. Loopはcycleをつなぐ

Loop は、一つの work cycle が終わったあと、何を条件として次の cycle を起こすかを定める構造である。

Trigger
   ↓
work cycle
   ↓
状態を確認
   ↓
├─ 続ける → 次の cycle
│
└─ 終了条件成立 → 終了

したがって Loop を見るときは、何回繰り返すかよりも、何が次を起こすのかを見る。

Task が仕事の単位を定め、Trigger が入口を定め、終了条件が出口を定める。

Loop は、それらを使って一つの cycle の次に何が起きるかを定める。

10. Loop controllerは次のcycleを起こす

Loop controller は、次の cycle を起こすかどうかを決めるものである。

Turn-based
    ↓
人間

Goal-based
    ↓
Goal の未達成

Time-based
    ↓
時間

Proactive
    ↓
外部 Event

どの Loop でも Agent が仕事をすることは変わらない。

違うのは、何が次の cycle を起こす判断を担うかである。

この違いによって、Loop は Turn-based、Goal-based、Time-based、Proactive に分けて考えられる。

Loop の種類は、何が Loop controller になるかによって決まる。

11. Turn-basedでは人間が次を起こす

Turn-based は、人間が結果を確認し、次の Prompt を与えることで次の cycle を起こす Loop である。

Prompt
  ↓
Task
  ↓
結果
  ↓
人間が確認
  ↓
次の Prompt
  ↓
次の Task

一つの Task が終わると、Agent の作業はいったん止まる。

その結果を見た人間が、

  • 続ける
  • 方向を変える
  • 別の Task を与える
  • そこで終了する

を判断する。

このとき、次の Task を起こす直接の Trigger は Prompt である。

そして、その Prompt を与えるかどうかを決めている人間が Loop controller である。

Turn-based では、Agent が自分で次へ進むのではない。

人間が cycle と cycle の間をつないでいる。

12. Goal-basedではGoalの未達成が次を起こす

Goal-based は、Goal が未達成である限り次の cycle を起こし、Goal に到達したら止まる Loop である。

work cycle
    ↓
Goal 達成？
 ├─ Yes → 終了
 │
 └─ No  → 次の cycle

Turn-based のように、人間が毎回次の Prompt を与える必要はない。

代わりに、Goal の状態が次へ進むかどうかを決める。

たとえば、

  • test がすべて通る
  • score が一定値以上になる
  • 指定した件数を処理する
  • 原因を特定する

といった、到達したかどうかを判定できる Goal を置く。

特に、tests passed や件数のような 外から明確に判定できる条件は強い。

Goal-based で重要なのは、Agent に「もう十分できた」と判断させることではない。

Goal の達成状態を判定し、未達成なら次の cycle へつなぐ。

Turn-based では人間が cycle をつなぐ。

Goal-based では、Goal の未達成状態が cycle と cycle の間をつなぐ。

13. Time-basedでは時間が次を起こす

Time-based は、時間を Trigger として次の cycle を起こす Loop である。

work cycle
    ↓
待つ
    ↓
Time
    ↓
次の cycle

たとえば、

  • 毎朝情報を集める
  • 5分ごとに状態を確認する
  • 一定時間ごとに新しい入力を確認する
  • 定期的に同じ処理を行う

といった仕事に使える。

毎回行う Task は同じでも、その間に外部の状態が変化する。

同じ Task
   ↑
時間の経過
   ↑
変化した外部状態

ここでいう Time は、Task を起こす Trigger としての時間である。

Task を止める時間上限は、Bound として扱う。

Time as Trigger  30分後にもう一度始める
Time as Bound    30分で終了する

Time as Trigger は、次の Task をいつ起こすかを定める。

Time as Bound は、今の Task をどこまで続けてよいかを定める。

どちらも時間を使うが、Trigger は入口を開き、Bound は出口を閉じる。

14. Proactiveでは外部世界が次を起こす

Proactive は、外部の Event や State の変化を Trigger として Task を起こす Loop である。

外部の変化
    ↓
 Trigger
    ↓
  Task
    ↓
  終了

たとえば、

  • 新しい bug report が来た
  • issue が作成された
  • dependency update が発生した
  • review request が来た

といった変化によって Task が始まる。

Turn-based と異なり、人間がその場で Prompt を与える必要はない。

重要なのは、一つの Task が終わっても、Task を発生させる仕組み自体は残り続けられることである。

Proactive routine
 │
 ├─ Event → Task A → 終了
 ├─ Event → Task B → 終了
 ├─ Event → Task C → 終了
 │
 └─ routine は残り続ける

ここでは、

個々の Task の寿命

と、

Task を発生させる仕組みの寿命

を分けて考える。

Proactive では、外部世界の変化が Task と Task の間をつないでいる。

15. Loopの種類はcontrolの置き場所の違いである

Turn-based、Goal-based、Time-based、Proactive の違いは、Agent が何をするかではない。

次の cycle を起こす control を、どこに置くかが違う。

同じ Task でも、

  • 人間に control を残す
  • Goal の未達成に渡す
  • 時間に渡す
  • 外部 Event に渡す

ことで、Loop の構造は変わる。

Task が同じでも、control の置き場所を変えれば運用は変わる。

16. Triggerと終了条件は別々に組み合わせられる

Task の入口と出口は、別々に選んで組み合わせられる。

たとえば、時間を Trigger にして Task を起こし、Goal に到達したら閉じることができる。

Time
 ↓
Task
 ↓
Goal 達成
 ↓
Task を閉じる
 ↓
次の Time まで待つ

同じように、外部 Event を Trigger にして Task を起こし、Goal に到達したら閉じることもできる。

Event
  ↓
Task
  ↓
Goal 達成
  ↓
Task を閉じる

つまり、何が始めるかと、何が閉じるかは独立して設計できる。

Loop Engineering は、Loop の種類を一つ選ぶことではない。

Task の入口と出口を組み合わせ、その間をどうつなぐかを設計することである。

17. 自律化はLoop controlを条件へ移す

Turn-based では、人間が多くの Loop control を担っている。

人間は、

  • Task を始める
  • 結果を確認する
  • 続けるか判断する
  • 止めるか判断する
  • 次の方向を決める
  • 次の Prompt を与える

という役割を持つ。

        人間
         │
 ┌───────┼───────┐
 ↓       ↓       ↓
開始    継続    終了
         │
         ↓
       次の Task

Loop を変えるということは、これらの判断を一つずつ明示的な条件へ移すことでもある。

Goal    → 続けるか、止めるか
Time    → いつ次を起こすか
Event   → いつ Task を起こすか

その結果、人間が毎回判断しなくても Loop をつなげられるようになる。

これは、Agent を突然賢くすることとは違う。

人間が担っていた Loop control の一部を、明示的な条件へ移していくことが自律化である。

18. Loopの長さは本質ではない

反復する仕事の設計では、Agent をどれだけ長く動かすかではなく、仕事を何によって始め、続け、止めるかを考える。

開始    何が仕事を始めるか
継続    何が次の cycle を起こすか
終了    何が仕事を止めるか

Loop の長さはさまざまである。

  • 数秒で Goal に到達する
  • 一日に一度だけ起動する
  • Event が来たときだけ動く
  • 必要な間だけ cycle を繰り返す

いずれも Loop として扱える。

ここで設計するのは、反復する仕事の制御条件である。

19. 何をLoopにするかは次のcycleを誰が起こすかで考える

何を Loop にするかは、単に その Task を繰り返せるかでは決まらない。

次の cycle を、誰が、あるいは何が起こすべきかを考える。

人間の判断が必要
    ↓
Turn-based

Goal の未達成で続けられる
    ↓
Goal-based

時間によって入力や状態が変わる
    ↓
Time-based

外部 Event が仕事の発生を示す
    ↓
Proactive

すべての control を人間から外す必要はない。

判断条件が曖昧であったり、人間の判断そのものに価値があるなら、Turn-based のままでよい。

人間を controller として残すことも、Loop の設計である。

20. Loopは三つの問いに分けて見る

Loop を考えるときは、仕事全体を一つの「自律性」として見るのではなく、三つの問いに分ける。

開始    何が Task を起こすか
反復    何が次の cycle を起こすか
終了    何が Task を止めるか

開始には Trigger がある。

反復には Loop controller がある。

終了には Goal、Thought、Bound などの条件がある。

これらを分ければ、人間が担う判断と、条件に任せられる判断を個別に考えられる。

Task がどう始まり、どうつながり、どう終わるかを分けて見る。

第III部　Goal・Verification・Bound

21. Goalは複数のcycleに共通するfinish lineになる

Goal-based Loop では、Goal が複数の cycle に共通する finish line になる。

やりたいこと
    ↓
進む方向

Goal
    ↓
finish line

たとえば、

高速化する

だけでは、どこで仕事を終えるかは決まらない。

Lighthouse score >= 90

のように、到達したかどうかを判定できる状態を置けば、Goal に到達するまで cycle をつなげられる。

cycle
  ↓
Goal 未達成
  ↓
cycle
  ↓
Goal 未達成
  ↓
cycle
  ↓
Goal 達成 → Task 終了

Goal は、それぞれの cycle が目指す共通の finish line を与える。

22. Goalは判定できる形で書く

Goal は、到達したかどうかを判定できる状態で書く。

たとえば、

品質を改善する

だけでは、進む方向は分かっても、どこで到達したかを明確に判定しにくい。

Goal には、

tests passed
score >= N
件数 = N
exit code = 0

のように、何が成立すれば到達したとみなすかを置く。

Verification は、その Goal が実際に成立したかを確かめる。

Goal
  ↓
成立したか？
  ↓
Verification で確かめる

Goal が到達条件を定め、Verification がその成立を確かめる。

23. BoundはGoalへ向かうLoopの許容範囲を決める

Bound は、Goal を目指す Loop で、どこまで試してよいかを決める境界である。

Goal とは別物である。

Goal
  ↓
どこまで行けば成功か

Bound
  ↓
どこまで試してよいか

言い換えると、

Goal  = finish line
Bound = guardrail

たとえば、

ホームページを高速化する
        ↓
Lighthouse >= 90
        ↓
最大5回

とすれば、

Goal   Lighthouse >= 90
Bound  最大5回

となる。

Bound は回数だけではない。

Bound
├─ Iteration  試行回数
├─ Time       時間
├─ Cost       コスト
├─ Scope      変更範囲
└─ Risk       危険性・不確実性

時間、試行回数、コストのような Bound は、上限に達したら Loop を止める。

Scope や Risk のような Bound は、その範囲を越えずに進める。

Goal が「どこまで行けば成功か」を決め、Bound が「成功を目指してどこまで許容するか」を決める。

24. Goalの達成はVerificationで確かめる

Goal を置いただけでは、その Goal が成立したことにはならない。

たとえば、

Goal
  ↓
tests passed

と定めても、Agent が「たぶん通る」と判断しただけでは十分ではない。

実際に test を実行し、その結果を確認する必要がある。

Goal
  ↓
Verification
  ↓
成立を確認

Goal が成立したかは、Verification で確かめる。

25. Verificationには層がある

Verification は、一つの確認だけで完結するとは限らない。

確認する対象によって、いくつかの層に分けられる。

Verification 確認するもの
Syntax 文法や形式が正しいか
Build build が成立するか
Test test が通るか
Runtime 実際に起動・実行できるか
Behavior 期待した動作をするか 
Syntax
  ↓
Build
  ↓
Test
  ↓
Runtime
  ↓
Behavior

Syntax が正しくても、build できるとは限らない。

Build できても、test が通るとは限らない。

Test が通っても、実際に期待した動作をするとは限らない。

下へ行くほど、実際の成果に近いものを確認する。

26. Verificationの結果が次の処理を変える

Verification は、結果を確認し、次に何をするかを判断するための材料を与える。

Act
 ↓
Verify
 ↓
├─ Pass → Stop
│
└─ Fail → Act

Pass なら、Goal が成立したことを確認して Task を閉じる。

Fail なら、その結果をもとに修正し、もう一度 Verification を行う。

作る
 ↓
確認する
 ↓
失敗を知る
 ↓
修正する
 ↓
もう一度確認する

Verification がなければ、Loop は同じ作業を繰り返すだけになりやすい。

Verification があることで、Loop は結果を見ながら次の処理を変えられる。

27. VerificationはGoalを同じ基準で確かめられるほど強い

Verification は、Goal が成立したかを同じ基準で確かめられるほど強い。

tests passed
score >= N
件数 = N
exit code = 0

このような Goal は、成立したかどうかを同じ基準で確かめやすい。

一方、

良い設計になった
自然な UI になった
十分に美しいコードになった

といった Goal は、機械的には確かめにくい。

明確に判定できる
      ↓
Verification が強い

判断が必要
      ↓
Verification が弱い

Verification の強さは、Goal が成立したかをどれだけ一貫した基準で確かめられるかによって決まる。

28. Verificationの深さで確認できる範囲が変わる

Verification の強さが「同じ基準で確かめられるか」を表すのに対して、深さは「どこまで実際の成果に近づいて確かめるか」を表す。

強さ  同じ基準で確かめられるか
深さ  どこまで実際の成果に近づいて確かめるか

同じ Goal でも、どこまで Verification するかによって、確認できる範囲は変わる。

たとえば、

Goal
  ↓
プログラムが正常に動作する

という同じ Goal に対しても、

Build      build が成立する
Test       test が通る
Runtime    実際に実行できる
Behavior   期待した動作をする

では、確認しているものが異なる。

同じ Goal
   ↓
Verification の深さ
   ↓
確認できた範囲

Goal は同じでも、Build まで確認した状態と、Behavior まで確認した状態では、Goal について確認できた範囲が異なる。

Verification の深さによって、その Task でどこまで確かめられたかが変わる。

第IV部　時間と再観測

29. Time-based Loopは状態を時間方向に再観測する

Time-based Loop は、時間を Trigger として、外部の状態をもう一度観測する機会を作る。

10:00  観測
11:00  観測
12:00  観測
13:00  観測

時間が来るたびに同じ対象を観測すると、前回から何が変わったかを見られる。

前回の状態
    ↓
時間経過
    ↓
今回の状態
    ↓
差分

Time-based Loop が、それ自体で問題を解決するとは限らない。

役割は、状態のスナップショットを時間方向につなぎ、変化をもう一度見る機会を作ることである。

Time-based Loop = Heartbeat
                  「また見る」

観測した変化によって、次の判断や別の Task、Goal が必要になることもある。

Time-based Loop は、時間方向に再観測の機会をつなぐ。

30. 仕事は同じで入力だけが変わる

Time-based Loop に向くのは、仕事の形が変わらず、入力だけが時間とともに変化する仕事である。

同じ Task
    ↓
異なる入力
    ↓
異なる現在の状態

たとえば「PR を確認する」という Task は同じでも、観測するたびに状態は変わる。

10:00  review comment が増えた
11:00  CI が失敗した
12:00  merge された
13:00  変化なし

毎回「何をする仕事か」から考え直す必要はない。

同じ Task を、変化した状態に対してもう一度行う。

逆に、毎回仕事そのものを決め直す必要があるものは、単純な Loop には向きにくい。

Task は同じでも、観測する世界は変わる。

31. Time budgetはBoundの一種である

Time budget は、Task に使ってよい時間の上限を決める Bound である。

時間は、使われる場所によって役割が違う。

Time-based Loop  = Trigger
Time budget      = Bound

Time-based Loop の Time は、時間が来たので始める。

Time budget の Time は、時間を使い切ったので止める。

第V部　委譲・監視・判定

32. 委譲はTaskの性質で決める

委譲は、Task が簡単か難しいかだけでは決めない。

Task
 │
 ├─ 間違ったときの影響
 ├─ Verification の強さ
 ├─ 判断の曖昧さ
 └─ 権限・安全性

これらによって、人間がどこまで離れてよいかが変わる。

影響が大きい
Verification が弱い
判断が曖昧
強い権限を使う
      ↓
人間を近くに置く

簡単な Task でも、間違えたときの影響が大きければ近くで見る必要がある。

難しい Task でも、結果を強く Verification できれば任せられる範囲は広がる。

委譲は、Agent の能力ではなく、Task の性質から考える。

33. Verificationの強さが委譲できる距離を決める

Agent にどこまで Loop を任せられるかは、Agent の能力だけでは決まらない。

何を Verification できるかにも強く依存する。

Verification が弱い
        ↓
人間が近くで確認する

Verification が強い
        ↓
Agent に任せられる範囲が広がる

結果を明確に確認できなければ、人間が近くで判断を補う必要がある。

結果を強く Verification できれば、途中の判断を Agent に任せ、人間は Task から離れやすくなる。

この距離を 監視距離 と考える。

Verification の強さが、Agent にどこまで任せ、人間がどこまで離れてよいかを決める。

34. MakerとCheckerを分ける

Maker は、成果物を作る役割である。

Checker は、その成果物を確かめる役割である。

Maker
  ↓
成果物
  ↓
Checker
  ↓
判定

Maker は、自分が作ったものについて、すでに一つの見方を持っている。

そのため、同じ視点のままでは誤りに気づきにくいことがある。

Checker を分ければ、成果物を別の context、別の視点から Verification できる。

作ることと、確かめることを分ける。

35. Verificationがあっても観測軸が足りないことがある

Verification が正しくても、観測する対象が足りないことがある。

正しく測れている
       ≠
必要なものを測れている

たとえば desktop performance を正しく Verification していても、重要なのが mobile experience なら十分ではない。

このとき、Verification が間違っているわけではない。

観測軸が足りない。

Verification
  ↓
見ているものは正しいか

観測軸
  ↓
見るべきものを見ているか

Verification の強さだけでなく、何を Verification するかも設計する。

36. Taskを委譲してもJudgmentは別に考える

Goal は、Task の到達条件を定める。

しかし、Goal が明確でも、その進め方や結果を採用してよいかまでは決まらない。

Goal
  ↓
到達したか

Judgment
  ↓
それでよいか

たとえば tests passed という Goal を達成しても、

  • 変更範囲は適切だったか
  • 互換性を壊していないか
  • 設計を複雑にしすぎていないか
  • その修正を採用すべきか

は別に判断する必要がある。

Task の実行は Agent に委譲できる。

一方、Judgment は、その仕事や結果を採用してよいかという判断である。

Task
  ↓
Agent に委譲できる

Judgment
  ↓
人間が担う

Agent が問題を解けることと、その解決を採用すべきことは同じではない。

仕事を任せることと、それでよいかを判断することは分けて考える。

37. 三つの判定を混ぜない

Task の結果には、異なる三つの判定がある。

Goal Evaluator
「条件を満たしたか？」
       ↓
Independent Checker
「成果物は正しいか？」
       ↓
Human Judgment
「採用すべきか？」

Goal Evaluator は、Goal が成立したかを判定する。

Independent Checker は、成果物そのものが正しいかを別の視点から確認する。

Human Judgment は、その成果物を採用してよいかを判断する。

Goal Evaluator      = Done
Independent Checker = Correct
Human Judgment      = Worth doing

Goal を達成しても、成果物が正しいとは限らない。

成果物が正しくても、それを採用すべきとは限らない。

Done / Correct / Worth doing は別である。

第VI部　Task / Loop の実践

38. 日常の反復作業は最初のLoop候補

Loop の候補を、新しく発明する必要はない。

人間がすでに繰り返している仕事を見る。

人間が繰り返している仕事
        ↓
Task はほぼ同じ
        ↓
Input だけが変わる
        ↓
Loop 候補

たとえば、

  • 毎朝 issue を確認する
  • 定期的に PR を確認する
  • 一定時間ごとに状態を確認する

といった仕事である。

仕事の形が同じで、観測する Input だけが変わるなら、Loop にしやすい。

繰り返している仕事は、すでに Loop の形を持っている。

39. LoopとGoalを組み合わせる

Loop と Goal は、競合するものではない。

異なる役割を組み合わせて使う。

Loop
  ↓
次の観測機会を作る

Goal
  ↓
見つかった仕事の finish line を作る

たとえば、

24時間ごとに bug issue を確認
        ↓
bug を発見
        ↓
修正
        ↓
tests passed
        ↓
Goal 達成

Loop は、時間方向に観測をつなぐ。

Goal は、そこで見つかった仕事の到達点を定める。

言い換えると、

Loop = Heartbeat
Goal = Finish line

である。

この例では、Loop が仕事を見つけ、Goal がその仕事の到達点を定める。

40. Progress conditionは前進を継続条件にする

Progress condition は、Loop が前進しているかを判定する条件である。

cycle
  ↓
前進した？
 ├─ Yes → 続ける
 │
 └─ No  → 継続を見直す

最大回数だけでは、Loop が意味のある仕事をしているかは分からない。

最大10 cycles
        ≠
10 cycles 前進する

たとえば、

各 cycle で
少なくとも 1 metric 改善

のように、前進そのものを条件にできる。

Progress condition は、Loop が動いているかではなく、進んでいるかを見る。

41. Stall conditionは停滞したLoopを止める

Stall condition は、Loop が前進しなくなったことを判定する条件である。

cycle
  ↓
前進なし
  ↓
cycle
  ↓
前進なし
  ↓
Stall → Loop を止める

Loop が動いていることと、前進していることは同じではない。

たとえば、

2 cycles 連続で改善なし
        ↓
終了

のように、停滞そのものを Loop の打ち切り条件にできる。

Progress condition が 進んでいるかを見るのに対して、Stall condition は 進まなくなったかを見る。

Stall condition は、Goal / Thought / Bound に並ぶ Task の終了軸ではなく、Loop の継続を打ち切るための条件である。

Stall condition は、動き続けるだけの Loop を止める。

42. 文章のルールを判断条件に変える

人間向けに書かれたルールは、そのままでは Loop の判断に使いにくいことがある。

そこで、文章の意味を判定できる条件へ変える。

文章のルール
    ↓
判定条件
    ↓
動作

たとえば、

「現在、翻訳の変更は受け付けない」

というルールがあるとする。

これを、

「変更内容が翻訳である？」
        ↓
Yes → 受け付けず閉じる
No  → 通常の確認を続ける

という形にすれば、Loop の中で判断に使える。

重要なのは、文章そのものを実行することではない。

文章に含まれている判断基準を取り出し、条件として使える形にする。

読めるルール
    ↓
判定できる条件
    ↓
実行できる判断

ルールを読めるだけの情報から、判断に使える条件へ変える。

43. 要約は正本ではない

長い Task や Loop では、現在地を短く伝えるために要約を使うことがある。

要約は Context を小さくするためには有効だが、元のルールや Goal、Bound を置き換えるものではない。

たとえば、

「既存APIは変更しない」

↓ 要約

「互換性を維持する」

↓ 次の要約

「互換性に配慮する」

最後の文は、最初のルールと同じ意味ではない。

要約を繰り返すと、情報が減るだけでなく、元の意味が少しずつ変わることがある。

正本
  ↓
要約
  ↓
要約
  ↓
意味がずれる

そのため、要約は現在状態を伝えるための派生情報として使い、判断の基準になる元の情報は必要に応じて正本へ戻って確認する。

要約がいつの間にか正本を置き換えないようにする。

44. Taskは小さな契約として書ける

実践では、Task に複数の制御条件を組み合わせて持たせることができる。

Task
 │
 ├─ Goal
 ├─ Progress condition
 ├─ Stall condition
 │
 └─ Bound
      ├─ Scope
      └─ Iteration

たとえば、

Task
  data-fetching layer を refactor

Goal
  Lighthouse >= 92
  LCP < 1.8s

Progress condition
  各 cycle で少なくとも 1 metric 改善

Stall condition
  2 cycle 連続で改善なし → 終了

Bound
  public API は変更しない
  最大 10 cycles

Goal は finish line を決める。

その周囲に、進み方、停滞、許容範囲を定める条件を置く。

Task は、仕事とその制御条件をまとめた小さな契約として書ける。

注釈

  • Lighthouse：Web ページの品質や performance を測定するツール。
  • LCP：Largest Contentful Paint。主要な大きな要素が表示されるまでの時間を表す performance 指標。
  • metric：測定値や評価指標の総称。この例では Lighthouse score や LCP などを指す。

第VII部　Loop の限界と停止

45. Loopは曖昧な判断を解消しない

Loop は、曖昧な判断基準を明確にしてくれる仕組みではない。

たとえば、

「この UI が良くなるまで続ける」

だけでは、終了条件が決まらない。

「良い」とは？
   │
   ├─ 誰にとって良いのか
   ├─ 何が良くなればよいのか
   └─ どう確かめるのか

が決まっていないからである。

Taste や主観的なデザインのように、人間の Judgment が必要な仕事は、終了を明確な条件だけで決めにくい。

Task を実行できる
        ≠
Task を Loop にできる

Agent が仕事を進められることと、その仕事の継続と終了を条件化できることは別である。

Loop は曖昧さを消さない。終了を条件として書ける仕事ほど Loop に向く。

第VIII部　製品固有の制約

46. 製品固有の制約は一般原理と分ける

Loop の一般原理と、製品ごとの実装上の制約は分けて考える。

一般原理
  │
  ├─ Trigger
  ├─ Goal
  ├─ Thought
  ├─ Verification
  ├─ Bound
  └─ Loop controller

        ↓

製品固有の制約
  │
  ├─ session の寿命
  ├─ schedule の保持期間
  ├─ 実行時間の上限
  └─ 利用できる権限

一般原理は、仕事をどう制御するかを定める。

製品固有の制約は、その制御をどこまで実装できるかを定める。

製品の仕様は変わる。

そのたびに、Loop の概念そのものを書き換える必要はない。

原理と実装を分ければ、製品が変わっても設計は残る。
