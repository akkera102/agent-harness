How to start, continue, verify, and stop an Agent's work

Purpose: To organize what starts, continues, verifies, and stops an Agent's work. This guide focuses on the control structures of Tasks and Loops and treats them separately from product-specific implementation details.

This guide does not recommend any single approach to autonomy. It is a guide to designing the conditions that govern how work starts, repeats, and ends, including cases where the human remains the Loop controller.

Part I — Basic Structure of a Task

1. What Is a Task?

A Task is a unit of work given to an Agent.

In ordinary interaction, a Task begins with a Prompt given by a human.

However, a Prompt is not the only thing that can initiate a Task. Time, an external event, or an unmet state can also become a Trigger.

Prompt / Time / Event / State
            ↓
           Task
            ↓
          Agent

In other words, a Task is not the Prompt itself. It should be understood as work that is initiated by a Trigger such as a Prompt and processed by an Agent.

2. A Trigger Defines the Start Condition of a Task

A Trigger is the start condition that determines what must happen for a Task to begin.

Trigger
   ↓
 Task
   ↓
 Work

In ordinary interaction, a Prompt given by a human is the Trigger.

But a Trigger is not limited to a Prompt.

  • a certain time arrives
  • an external event occurs
  • a state changes
  • the Goal has not yet been achieved

Conditions such as these can also start a Task.

Prompt / Time / Event / State
            ↓
         Trigger
            ↓
           Task

What matters is to separate what the Task does from what causes that Task to begin.

The Trigger is not the content of the Task.

As the entry point of the Task, it defines when the work begins.

3. Give a Task an End Condition

When defining a Task, decide not only what it does, but also what will count as the end of that Task.

End conditions can be considered along three main axes.

Goal     End because the target state was reached
Thought  End because a judgment can be made
Bound    End because a limit was reached

A single Task does not necessarily have only one end condition.

Task
 │
 ├─ Goal
 ├─ Thought
 ├─ Bound
 │
 ├─ Goal + Thought
 ├─ Goal + Bound
 ├─ Thought + Bound
 │
 └─ Goal + Thought + Bound

For example, a Task can pursue a Goal while using a Bound as its upper limit, or it can end early through Thought once sufficient grounds for judgment have been obtained.

What matters is not to make the Agent decide from scratch each time whether it should keep going, but to give the Task itself axes for deciding when to end.

4. A Goal Defines the Target State of a Task

A Goal specifies what state must hold for the Task to be considered to have reached its intended destination.

Task
 ↓
Work
 ↓
Goal

For example:

  • the artifact is complete
  • the tests pass
  • the cause has been identified

These are states for which it is possible to judge whether they have been reached.

A Goal is not an instruction describing what work to perform.

As the destination of the Task, it defines what must become true.

5. Thought Stops When There Is No Longer a Reason to Keep Thinking About the Task

Thought is an end condition that says to stop when further thinking about the Task is no longer likely to change the judgment.

Task
 ↓
Investigation / reasoning
 ↓
New information for judgment is obtained
 ↓
Think further

Continue this process until a state such as the following is reached:

  • sufficient grounds have been obtained
  • the hypotheses have been narrowed as far as necessary
  • what should be checked next has become clear
  • further thinking is unlikely to change the judgment materially

At that point, the Task can end.

Thought does not mean that “the Agent feels it has thought enough.”

Stop when it can no longer explain what further thinking would change.

Where Goal defines the target state of a Task and Bound defines the permitted range of a Task, Thought defines how much reasoning and supporting basis are needed for judgment.

6. A Bound Defines the Permitted Range of a Task

A Bound is a boundary that determines how far a Task may proceed.

Task
 ↓
Proceed within the permitted range
 ↓
Do not cross the Bound

A Bound can cover, for example:

  • time
  • number of attempts
  • cost
  • scope of changes
  • risk

A Bound such as time, number of attempts, or cost closes the Task when the upper limit is reached.

A Bound such as scope of changes or risk lets the Task proceed without crossing that boundary.

For work such as investigation or exploration, where partial results still have value, reaching the limit should not be treated as having forced the Goal into a completed state. Instead, return what has been learned so far and what remains unresolved.

The time discussed here is different from Time used as a Trigger to initiate the Task again.

A Bound defines how far a Task pursuing a Goal is allowed to proceed.

7. End Conditions Can Be Combined

Goal, Thought, and Bound do not have to be used one at a time.

They can be combined according to the nature of the Task.

Combination How to think about ending
Goal + Thought Pursue the Goal, but stop once sufficient information for judgment has been obtained
Goal + Bound Pursue the Goal, but stop when the Bound is reached
Thought + Bound Stop once sufficient information for judgment has been obtained; if it is not obtained, stop at the Bound
Goal + Thought + Bound Stop when any one of Goal, Thought, or Bound is satisfied

For example, with Goal + Thought + Bound:

Task
 ↓
Pursue the Goal
 ↓
├─ Goal achieved     → End
├─ Thought satisfied → End
└─ Bound reached     → End

These three endings do not mean the same thing.

Goal     End because the target state was reached
Thought  End because a judgment can be made
Bound    End because a limit was reached

When a Task ends through Thought or Bound, the Goal may still be unachieved.

In that case, do not treat the Goal as achieved. Close the Task while preserving the current position, what is known, and what is still missing.

A Task ending is not the same as its Goal being achieved.

8. Separate the Entry and Exit of a Task

A Task can be understood by separating the entry point that determines what starts it from the exit point that determines what stops it.

Human / Time / Event / State
            ↓
          Trigger
            ↓
           Task
            ↓
    Goal / Thought / Bound

On the entry side, look at what initiates the Task.

On the exit side, look at what stops the Task.

Time can be used as a Trigger at the entry and as a Bound at the exit.

Entry Time    Start because the time has arrived
Exit Bound    End because the time limit has been reached

The entry and exit can be combined independently.

The combination of entry and exit defines the shape of the Task.

Part II — Basic Structure of a Loop

9. A Loop Connects Cycles

A Loop is a structure that defines what condition causes the next cycle to begin after one work cycle has ended.

Trigger
   ↓
work cycle
   ↓
Check the state
   ↓
├─ Continue → next cycle
│
└─ End condition satisfied → End

Therefore, when examining a Loop, look not primarily at how many times it repeats, but at what causes the next cycle to begin.

A Task defines the unit of work, a Trigger defines the entry point, and end conditions define the exit point.

A Loop uses them to determine what happens after one cycle and before the next.

10. The Loop Controller Initiates the Next Cycle

The Loop controller is what decides whether the next cycle should begin.

Turn-based
    ↓
  Human

Goal-based
    ↓
Unachieved Goal

Time-based
    ↓
   Time

Proactive
    ↓
External Event

In every Loop, the Agent still performs the work.

What differs is what is responsible for deciding whether to start the next cycle.

This difference lets us think of Loops as Turn-based, Goal-based, Time-based, or Proactive.

The type of Loop is determined by what serves as its Loop controller.

11. In Turn-Based Loops, the Human Initiates the Next Cycle

Turn-based is a Loop in which a human reviews the result and initiates the next cycle by giving the next Prompt.

Prompt
  ↓
Task
  ↓
Result
  ↓
Human reviews
  ↓
Next Prompt
  ↓
Next Task

When one Task ends, the Agent's work stops for the moment.

The human who sees the result decides whether to:

  • continue
  • change direction
  • give a different Task
  • end there

At this point, the direct Trigger that initiates the next Task is the Prompt.

And the human who decides whether to provide that Prompt is the Loop controller.

In a Turn-based Loop, the Agent does not move on by itself.

The human connects one cycle to the next.

12. In Goal-Based Loops, an Unachieved Goal Initiates the Next Cycle

Goal-based is a Loop that initiates the next cycle while the Goal remains unachieved, and stops once the Goal is reached.

work cycle
    ↓
Goal achieved?
 ├─ Yes → End
 │
 └─ No  → next cycle

Unlike a Turn-based Loop, a human does not need to provide the next Prompt every time.

Instead, the state of the Goal determines whether the Loop proceeds.

For example, the Goal can be a state whose attainment can be judged, such as:

  • all tests pass
  • a score reaches or exceeds a threshold
  • a specified number of items are processed
  • the cause is identified

Conditions that are clearly decidable from outside, such as tests passing or a count reaching a value, are especially strong.

What matters in a Goal-based Loop is not to let the Agent decide that “this is probably enough.”

Determine whether the Goal has been achieved, and if it has not, connect to the next cycle.

In a Turn-based Loop, a human connects the cycles.

In a Goal-based Loop, the unachieved state of the Goal connects one cycle to the next.

13. In Time-Based Loops, Time Initiates the Next Cycle

Time-based is a Loop that uses time as the Trigger for starting the next cycle.

work cycle
    ↓
  Wait
    ↓
  Time
    ↓
next cycle

For example, it can be used for work such as:

  • gathering information every morning
  • checking a state every five minutes
  • checking for new input at regular intervals
  • performing the same process periodically

The Task performed each time may be the same, while the external state changes in between.

Same Task
   ↑
Passage of time
   ↑
Changed external state

The Time discussed here is time as a Trigger that initiates the Task.

A time limit that stops the Task is treated as a Bound.

Time as Trigger  Start again in 30 minutes
Time as Bound    End after 30 minutes

Time as Trigger defines when to initiate the next Task.

Time as Bound defines how long the current Task may continue.

Both use time, but a Trigger opens the entry, while a Bound closes the exit.

14. In Proactive Loops, the External World Initiates the Next Cycle

Proactive is a Loop that uses an external Event or a change in State as the Trigger for initiating a Task.

External change
    ↓
 Trigger
    ↓
  Task
    ↓
  End

For example, a Task can begin when:

  • a new bug report arrives
  • an issue is created
  • a dependency update occurs
  • a review request arrives

Unlike a Turn-based Loop, a human does not need to provide a Prompt at that moment.

What matters is that even after one Task ends, the mechanism that generates Tasks can remain active.

Proactive routine
 │
 ├─ Event → Task A → End
 ├─ Event → Task B → End
 ├─ Event → Task C → End
 │
 └─ the routine remains active

Here, distinguish between:

the lifetime of each individual Task

and

the lifetime of the mechanism that generates Tasks.

In a Proactive Loop, changes in the external world connect one Task to the next.

15. Loop Types Differ by Where Control Is Placed

The difference among Turn-based, Goal-based, Time-based, and Proactive Loops is not what the Agent does.

The difference is where control for initiating the next cycle is placed.

Even with the same Task, the Loop structure changes depending on whether control is:

  • kept with the human
  • handed to the unachieved state of the Goal
  • handed to time
  • handed to an external Event

Even when the Task is the same, changing where control is placed changes the operation.

16. Triggers and End Conditions Can Be Combined Independently

The entry and exit of a Task can be selected and combined independently.

For example, time can be used as the Trigger that initiates a Task, and the Task can close once the Goal is reached.

Time
 ↓
Task
 ↓
Goal achieved
 ↓
Close the Task
 ↓
Wait until the next Time

Likewise, an external Event can be used as the Trigger that initiates a Task, and the Task can close once the Goal is reached.

Event
  ↓
Task
  ↓
Goal achieved
  ↓
Close the Task

In other words, what starts the Task and what closes it can be designed independently.

Loop Engineering is not about choosing one Loop type.

It is about combining the entry and exit of a Task and designing how the space between them is connected.

17. Making a Loop More Autonomous Moves Loop Control into Conditions

In a Turn-based Loop, the human carries much of the Loop control.

The human:

  • starts the Task
  • reviews the result
  • decides whether to continue
  • decides whether to stop
  • decides the next direction
  • provides the next Prompt
        Human
         │
 ┌───────┼───────┐
 ↓       ↓       ↓
Start  Continue   End
         │
         ↓
      Next Task

Changing the Loop also means moving these judgments, one by one, into explicit conditions.

Goal    → whether to continue or stop
Time    → when to initiate the next cycle
Event   → when to initiate a Task

As a result, the Loop can continue from one cycle to the next without requiring a human judgment every time.

This is different from suddenly making the Agent smarter.

Making a Loop more autonomous means moving part of the Loop control previously carried by the human into explicit conditions.

18. Loop Length Is Not the Essential Point

When designing repeated work, think not about how long to keep the Agent running, but about what starts, continues, and stops the work.

Start      What starts the work
Continue   What initiates the next cycle
End        What stops the work

Loops can have very different lengths.

  • a Goal is reached in a few seconds
  • the Loop runs only once per day
  • it runs only when an Event arrives
  • it repeats cycles only for as long as necessary

All of these can be treated as Loops.

What is being designed here is the control conditions for repeated work.

19. Decide What Should Be a Loop by Asking Who or What Should Initiate the Next Cycle

Whether something should be a Loop is not determined simply by whether the Task can be repeated.

Ask who or what should initiate the next cycle.

Human judgment is required
    ↓
Turn-based

An unachieved Goal can keep it going
    ↓
Goal-based

Input or state changes over time
    ↓
Time-based

An external Event indicates that work has arisen
    ↓
Proactive

There is no need to move all control away from the human.

If the judgment conditions are ambiguous, or if human judgment itself has value, leaving the Loop Turn-based is appropriate.

Keeping the human as the controller is also a Loop design.

20. View a Loop as Three Questions

When thinking about a Loop, do not treat the entire work process as one undifferentiated concept of “autonomy.” Separate it into three questions.

Start       What initiates the Task
Repeat      What initiates the next cycle
End         What stops the Task

Start has a Trigger.

Repeat has a Loop controller.

End has conditions such as Goal, Thought, and Bound.

Separating them lets you consider individually which judgments remain with the human and which can be entrusted to conditions.

Look separately at how the Task begins, how it connects to what follows, and how it ends.

Part III — Goal, Verification, and Bound

21. A Goal Becomes the Finish Line Shared Across Multiple Cycles

In a Goal-based Loop, the Goal becomes the finish line shared across multiple cycles.

What you want to do
    ↓
Direction of progress

Goal
    ↓
finish line

For example:

Make it faster

by itself does not determine where the work should end.

If you set a state whose attainment can be judged, such as:

Lighthouse score >= 90

then the cycles can remain connected until that Goal is reached.

cycle
  ↓
Goal not achieved
  ↓
cycle
  ↓
Goal not achieved
  ↓
cycle
  ↓
Goal achieved → Task ends

A Goal gives every cycle a common finish line to aim for.

22. Write a Goal in a Form That Can Be Judged

A Goal should be written as a state for which it is possible to judge whether it has been reached.

For example:

Improve quality

may indicate a direction, but it does not make it easy to determine clearly when the destination has been reached.

A Goal should specify what must become true for the destination to be considered reached, such as:

tests passed
score >= N
count = N
exit code = 0

Verification checks whether that Goal actually holds.

Goal
  ↓
Does it hold?
  ↓
Check with Verification

The Goal defines the attainment condition, and Verification checks whether it holds.

23. A Bound Defines the Permitted Range of a Loop Pursuing a Goal

A Bound is the boundary that determines how far a Loop may proceed while pursuing a Goal.

It is different from the Goal.

Goal
  ↓
How far must we go for success?

Bound
  ↓
How far are we allowed to try?

In other words:

Goal  = finish line
Bound = guardrail

For example:

Make the homepage faster
        ↓
Lighthouse >= 90
        ↓
At most 5 attempts

becomes:

Goal   Lighthouse >= 90
Bound  At most 5 attempts

A Bound is not limited to the number of attempts.

Bound
├─ Iteration  number of attempts
├─ Time       time
├─ Cost       cost
├─ Scope      scope of changes
└─ Risk       danger / uncertainty

A Bound such as Time, Iteration, or Cost stops the Loop when the upper limit is reached.

A Bound such as Scope or Risk lets the Loop proceed without crossing that range.

The Goal determines “how far we must go for success,” while the Bound determines “how far we are allowed to go in pursuit of success.”

24. Verify Goal Attainment with Verification

Merely defining a Goal does not mean that the Goal has been achieved.

For example, even if the Goal is defined as:

Goal
  ↓
tests passed

it is not enough for the Agent merely to judge that “they probably pass.”

The test must actually be run and its result checked.

Goal
  ↓
Verification
  ↓
Confirm that it holds

Whether the Goal holds is checked through Verification.

25. Verification Has Layers

Verification does not necessarily end with a single check.

It can be divided into several layers depending on what is being checked.

Verification What it checks
Syntax Whether the syntax or format is correct
Build Whether the build succeeds
Test Whether the tests pass
Runtime Whether it actually starts and runs
Behavior Whether it behaves as expected 
Syntax
  ↓
Build
  ↓
Test
  ↓
Runtime
  ↓
Behavior

Correct syntax does not guarantee that the code will build.

A successful build does not guarantee that the tests will pass.

Passing tests do not guarantee that the result will actually behave as expected.

The farther down you go, the closer the check is to the actual outcome.

26. Verification Results Change What Happens Next

Verification checks the result and provides information for deciding what to do next.

Act
 ↓
Verify
 ↓
├─ Pass → Stop
│
└─ Fail → Act

On Pass, confirm that the Goal holds and close the Task.

On Fail, make a correction based on that result and perform Verification again.

Create
 ↓
Check
 ↓
Learn that it failed
 ↓
Correct
 ↓
Check again

Without Verification, a Loop can easily become repeated execution of the same work.

Verification lets the Loop change its next action in response to the result.

27. Verification Is Stronger When It Can Check the Goal Against a Consistent Criterion

Verification is stronger when whether the Goal holds can be checked against the same criterion each time.

tests passed
score >= N
count = N
exit code = 0

Goals like these make it easy to check attainment against a consistent criterion.

By contrast, Goals such as:

The design became good
The UI became natural
The code became sufficiently beautiful

are harder to check mechanically.

Clearly decidable
      ↓
Verification is strong

Judgment is required
      ↓
Verification is weak

The strength of Verification is determined by how consistently it can check whether the Goal has been achieved.

28. Verification Depth Changes What Can Be Confirmed

Where the strength of Verification describes “whether it can be checked against the same criterion,” its depth describes “how close the check gets to the actual outcome.”

Strength  Can it be checked against the same criterion?
Depth     How close does the check get to the actual outcome?

Even with the same Goal, what can be confirmed changes depending on how far Verification goes.

For example, for the same Goal:

Goal
  ↓
The program operates correctly

the following checks confirm different things:

Build      the build succeeds
Test       the tests pass
Runtime    it can actually be executed
Behavior   it behaves as expected

Same Goal
   ↓
Depth of Verification
   ↓
Range that has been confirmed

Even though the Goal is the same, confirming only through Build and confirming through Behavior establish different ranges of what has actually been confirmed about the Goal.

The depth of Verification changes how much has actually been confirmed in that Task.

Part IV — Time and Re-Observation

29. A Time-Based Loop Re-Observes State Along the Time Axis

A Time-based Loop uses time as a Trigger to create another opportunity to observe external state.

10:00  Observe
11:00  Observe
12:00  Observe
13:00  Observe

Observing the same target whenever the time arrives makes it possible to see what has changed since the previous observation.

Previous state
    ↓
Passage of time
    ↓
Current state
    ↓
Difference

A Time-based Loop does not necessarily solve the problem by itself.

Its role is to connect snapshots of state along the time axis and create opportunities to look again for change.

Time-based Loop = Heartbeat
                  “look again”

Observed changes may create the need for a new judgment, another Task, or a Goal.

A Time-based Loop connects opportunities for re-observation along the time axis.

30. The Work Stays the Same While Only the Input Changes

A Time-based Loop is well suited to work where the shape of the work remains the same and only the input changes over time.

Same Task
    ↓
Different input
    ↓
Different current state

For example, the Task “check the PR” remains the same even though the observed state changes each time.

10:00  review comments increased
11:00  CI failed
12:00  merged
13:00  no change

There is no need to rethink what kind of work to do every time.

Perform the same Task again against the changed state.

By contrast, work that requires deciding the nature of the work itself from scratch each time is less suited to a simple Loop.

The Task may remain the same while the world being observed changes.

31. A Time Budget Is a Type of Bound

A Time budget is a Bound that sets the maximum amount of time that may be spent on a Task.

Time has different roles depending on where it is used.

Time-based Loop  = Trigger
Time budget      = Bound

The Time in a Time-based Loop means start because the time has arrived.

The Time in a Time budget means stop because the allotted time has been used up.

Part V — Delegation, Supervision, and Judgment

32. Decide Delegation by the Nature of the Task

Delegation should not be decided only by whether the Task is easy or difficult.

Task
 │
 ├─ Impact if it is wrong
 ├─ Strength of Verification
 ├─ Ambiguity of judgment
 └─ Authority / safety

These factors change how far the human can step away.

High impact
Weak Verification
Ambiguous judgment
Broad authority is used
      ↓
Keep the human close

Even a simple Task may need close human supervision if an error would have a large impact.

Even a difficult Task can be entrusted more broadly when its result can be strongly verified.

Think about delegation from the nature of the Task, not from the capability of the Agent.

33. The Strength of Verification Determines the Delegation Distance

How much of a Loop can be entrusted to an Agent is not determined only by the Agent's capability.

It also depends strongly on what can be verified.

Verification is weak
        ↓
Human checks from nearby

Verification is strong
        ↓
The range entrusted to the Agent expands

If the result cannot be checked clearly, the human must remain close enough to supplement the judgment.

If the result can be strongly verified, more intermediate judgments can be left to the Agent and the human can move farther away from the Task.

Think of this distance as supervision distance.

The strength of Verification determines how much can be entrusted to the Agent and how far the human can step away.

34. Separate the Maker and the Checker

The Maker is the role that creates the artifact.

The Checker is the role that checks that artifact.

Maker
  ↓
Artifact
  ↓
Checker
  ↓
Assessment

The Maker already has one perspective on what it created.

For that reason, staying within the same perspective can make some errors harder to notice.

Separating the Checker makes it possible to verify the artifact from a different context and a different perspective.

Separate making from checking.

35. Even with Verification, the Observation Axes May Be Insufficient

Even when Verification is correct, the set of things being observed can still be insufficient.

Measuring correctly
       ≠
Measuring what is needed

For example, desktop performance may be verified correctly, but if mobile experience is what matters, that is not sufficient.

In that case, the Verification itself is not wrong.

The observation axes are insufficient.

Verification
  ↓
Is what we are looking at correct?

Observation axes
  ↓
Are we looking at what should be observed?

Design not only the strength of Verification, but also what is being verified.

36. Treat Judgment Separately Even When the Task Is Delegated

A Goal defines the attainment condition of the Task.

But even with a clear Goal, that does not decide whether the way the work was carried out or the resulting artifact should be accepted.

Goal
  ↓
Was it reached?

Judgment
  ↓
Is this acceptable?

For example, even after achieving the Goal tests passed, separate judgments are still needed about questions such as:

  • Was the scope of changes appropriate?
  • Was compatibility preserved?
  • Did the design become too complex?
  • Should this change actually be adopted?

Execution of the Task can be delegated to the Agent.

Judgment, by contrast, is the decision about whether the work or its result should be adopted.

Task
  ↓
Can be delegated to the Agent

Judgment
  ↓
Remains with the human

The fact that an Agent can solve a problem does not mean that its solution should be adopted.

Separate entrusting the work from deciding whether the result is acceptable.

37. Do Not Mix Three Different Evaluations

A Task result involves three different evaluations.

Goal Evaluator
“Was the condition satisfied?”
       ↓
Independent Checker
“Is the artifact correct?”
       ↓
Human Judgment
“Should it be adopted?”

The Goal Evaluator determines whether the Goal holds.

The Independent Checker examines the artifact itself from another perspective to determine whether it is correct.

Human Judgment decides whether that artifact should be adopted.

Goal Evaluator       = Done
Independent Checker  = Correct
Human Judgment       = Worth doing

Achieving the Goal does not guarantee that the artifact is correct.

Even a correct artifact does not necessarily mean that it should be adopted.

Done / Correct / Worth doing are distinct.

Part VI — Task / Loop in Practice

38. Everyday Repeated Work Is the First Place to Look for Loop Candidates

There is no need to invent new Loop candidates from scratch.

Look at work that humans are already repeating.

Work already repeated by humans
        ↓
Task is mostly the same
        ↓
Only the Input changes
        ↓
Loop candidate

For example:

  • check issues every morning
  • check PRs periodically
  • check a state at regular intervals

If the shape of the work remains the same and only the observed Input changes, it is easy to turn the work into a Loop.

Repeated work already has the shape of a Loop.

39. Combine Loops and Goals

Loops and Goals do not compete with one another.

They have different roles and can be combined.

Loop
  ↓
Create the next opportunity to observe

Goal
  ↓
Create the finish line for work that was found

For example:

Check bug issues every 24 hours
        ↓
Find a bug
        ↓
Fix it
        ↓
tests passed
        ↓
Goal achieved

The Loop connects observations along the time axis.

The Goal defines the destination of the work found there.

In other words:

Loop = Heartbeat
Goal = Finish line

In this example, the Loop finds the work, and the Goal defines that work's destination.

40. A Progress Condition Makes Forward Movement a Condition for Continuing

A Progress condition is a condition that determines whether the Loop is making progress.

cycle
  ↓
Did it make progress?
 ├─ Yes → Continue
 │
 └─ No  → Reconsider continuation

A maximum number of iterations alone does not tell you whether the Loop is doing meaningful work.

At most 10 cycles
        ≠
Make progress for 10 cycles

For example, forward movement itself can be made a condition:

In each cycle,
improve at least 1 metric

A Progress condition checks not whether the Loop is moving, but whether it is moving forward.

41. A Stall Condition Stops a Loop That Has Stopped Making Progress

A Stall condition is a condition that determines that the Loop is no longer making progress.

cycle
  ↓
No progress
  ↓
cycle
  ↓
No progress
  ↓
Stall → Stop the Loop

A Loop running is not the same as a Loop making progress.

For example, stagnation itself can be used as a condition for terminating the Loop:

No improvement for 2 consecutive cycles
        ↓
End

Where a Progress condition asks whether progress is being made, a Stall condition asks whether progress has stopped.

A Stall condition is not another Task-ending axis alongside Goal / Thought / Bound. It is a condition for stopping the Loop from continuing.

A Stall condition stops a Loop that would otherwise only keep moving without making progress.

42. Turn Written Rules into Decision Conditions

Rules written for humans can be difficult to use directly for Loop decisions.

So transform the meaning of the prose into conditions that can be evaluated.

Written rule
    ↓
Evaluable condition
    ↓
Action

For example, suppose there is a rule:

“Translation changes are not currently being accepted.”

It can be transformed into:

“Is this change a translation change?”
        ↓
Yes → Do not accept it; close
No  → Continue the normal checks

so that it can be used for decisions inside the Loop.

The important point is not to execute the prose itself.

Extract the decision criterion contained in the prose and put it into a form that can be used as a condition.

Readable rule
    ↓
Evaluable condition
    ↓
Actionable decision

Turn information that can merely be read as a rule into a condition that can be used for decision-making.

43. A Summary Is Not the Source of Truth

Long Tasks and Loops sometimes use summaries to communicate the current position briefly.

A summary is useful for reducing Context, but it does not replace the original rules, Goal, or Bound.

For example:

“Do not change the existing API.”

↓ Summary

“Maintain compatibility.”

↓ Next summary

“Be mindful of compatibility.”

The final sentence does not have the same meaning as the original rule.

Repeated summarization can not only remove information but also change the original meaning little by little.

Source of truth
  ↓
Summary
  ↓
Summary
  ↓
Meaning drifts

Therefore, use summaries as derived information for communicating the current state, and return to the source of truth when necessary to check the original information that serves as the basis for judgment.

Do not let a summary quietly replace the source of truth.

44. A Task Can Be Written as a Small Contract

In practice, a Task can combine multiple control conditions.

Task
 │
 ├─ Goal
 ├─ Progress condition
 ├─ Stall condition
 │
 └─ Bound
      ├─ Scope
      └─ Iteration

For example:

Task
  refactor the data-fetching layer

Goal
  Lighthouse >= 92
  LCP < 1.8s

Progress condition
  improve at least 1 metric in each cycle

Stall condition
  no improvement for 2 consecutive cycles → End

Bound
  do not change the public API
  at most 10 cycles

The Goal defines the finish line.

Around it, place conditions that define how to make progress, how to detect stagnation, and what range is permitted.

A Task can be written as a small contract that combines the work itself with its control conditions.

Notes

  • Lighthouse: A tool for measuring Web page quality and performance.
  • LCP: Largest Contentful Paint. A performance metric representing how long it takes for the main large content element to be displayed.
  • metric: A general term for a measured value or evaluation indicator. In this example, it includes values such as Lighthouse score and LCP.

Part VII — Limits and Stopping of Loops

45. A Loop Does Not Resolve Ambiguous Judgment

A Loop is not a mechanism that makes ambiguous judgment criteria clear.

For example:

“Continue until this UI becomes good.”

by itself does not define an end condition.

What does “good” mean?
   │
   ├─ Good for whom?
   ├─ What must improve?
   └─ How will it be checked?

These questions remain unresolved.

For work that requires Human Judgment, such as taste or subjective design, it is difficult to define the end entirely through explicit conditions.

Can execute the Task
        ≠
Can turn the Task into a Loop

The fact that an Agent can perform the work is different from being able to express the continuation and ending of that work as conditions.

A Loop does not remove ambiguity. Work is better suited to a Loop when its ending can be written as conditions.

Part VIII — Product-Specific Constraints

46. Separate Product-Specific Constraints from General Principles

General principles of Loops should be considered separately from implementation constraints specific to a product.

General principles
  │
  ├─ Trigger
  ├─ Goal
  ├─ Thought
  ├─ Verification
  ├─ Bound
  └─ Loop controller

        ↓

Product-specific constraints
  │
  ├─ session lifetime
  ├─ schedule retention period
  ├─ execution time limit
  └─ available permissions

General principles define how the work is controlled.

Product-specific constraints define how far that control can be implemented.

Product specifications change.

There is no need to rewrite the concept of a Loop itself each time they change.

Separating principles from implementation allows the design to survive product changes.
