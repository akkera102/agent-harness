探索、証拠、負担、仕組み、判断、知識の流れを観測する

目的: Agent を使った探索・実装・検証の中で、何が進展し、何が成立し、人間にどの負担や判断が残り、仕組みや知識がどう働いているかを観測するための視点を整理する。

本書は特定の運用手順や自律化方式を定めるものではない。探索、証拠、負担、仕組み、判断、知識の流れを分けて見ることで、どこに問題があり、次に何を変えるべきかを判断するための観測ガイドである。

I. 探索を進める

1. 確認事項の粒度を見る

探索が停滞しているときは、確認事項を次の判断に使える単位へ分けられるかを見る。

たとえば、

  • 候補を一つ消せた
  • 次に見る場所が決まった
  • 仮説の一部を否定できた
  • 次の確認事項が見つかった

このような変化があれば、その確認は次の判断に使える。

次の判断を変えられる粒度になっているかを見る。

2. 候補集合の変化を見る

候補リストでは、

A
B
C

から Bではない と分かれば、

A
C

へ問題が変化する。

直接確認できない対象を扱うときは、観測した事実から候補を組み立てる。

そのため、候補リストの中に正解があるとは限らない。A、B、C のすべてが間違っている可能性も残る。

未知の D が新たに見つかり、候補が増えることも進展である。以前の候補集合が不完全だったと分かったからである。

理解が進んでも、確信度が上がるとは限らない。

問題の形が変わったら進展である。

3. 探索は decision gap で制御する

問いは探索の入口を与える。

一方で、複数の判断候補が残っているとき、その候補を区別するために足りない情報を decision gap（判断の差を埋めるために不足している情報）と考える。

たとえば、原因候補が A と B に絞られているなら、A と B を区別できる一つの観測を探す。

探索の初期には広く読む必要がある。候補が見え始めた後は、decision gap を基準に観測先を絞る。

探索先は、関係の深さではなく、判断を変えられるかで選ぶ。

4. 仮説を観測可能にする

仮説や設計判断をそのまま議論し続けるより、最小の試作や実験によって観測可能な形へ変えた方が早いことがある。

議論に使う時間、試作や実験に使う時間、そこから得られる知見を比べる。

議論より早く観測できるなら、観測へ移る。

II. 成立と証拠を判定する

5. 成果物を成果にしない

コード、文書、道具、報告、検査結果など、Agent が作った成果物は、作られただけでは完成品ではない。

すべてを試作として見る。

重要なのは、その試作によって何が確認できたか、目的としていた状態が本当に成立したかである。

Agent が作った成果物は、成立が確認されるまでは試作として扱う。

6. 変更は、失敗を再投入して確かめる

変更は、書いた時点では改善ではない。
実装した時点でも、まだ改善とは限らない。

ただし、すべての変更に大規模な試験が必要なわけではない。
変更の大きさではなく、失敗したときの影響に応じて再現の強さを変える。

Rule → 反例
手順 → 失敗場面
Harness → 境界到達
復旧処理 → 中断と再開

同じ反例で何度もRuleが破られるなら、そのRuleは文章だけで守らせるには弱い可能性がある。
その場合は、文章を増やすのではなく、Harnessや構造へ移せないかを見る。

失敗を直す変更は、以前の失敗を変えられたときに初めて確認される。

7. 合格は完成ではなく昇格である

試作の前提、観測範囲、証拠を確認する。

ここでの合格は、永久に正しいという意味ではない。

現在の前提、観測範囲、証拠のもとで、次の判断や作業の根拠として使ってよいという意味である。

合格は完成ではなく、次に使える状態への昇格である。

8. Evidence から Claim への推論を見る

Evidence から Claim（主張）へ進む間には推論がある。

疑い方は、少なくとも三つに分けられる。

結論を疑う
    Claim 自体が間違っていないか

証拠を疑う
    Evidence 自体を信用できるか

推論を疑う
    Evidence から Claim への推論が成立しているか

特に「推論を疑う」は、観測が正しい場合にも残る。

たとえば、

Evidence
    値 X を変えると出力 Y が変わった

Claim
    X が Y を直接制御している

という推論があったとする。

観測そのものは正しくても、途中に別の状態や変換が存在するなら、Claim は強すぎるかもしれない。

同じことは、再現結果にも起こる。

Evidence
    ある設定で実機と同じ出力を再現できた

Claim
    元の実装も同じ仕組みを使っている

前者が成立しても、後者まで証明されたとは限らない。

正しい Evidence から、強すぎる Claim へ飛んでいないかを見る。

9. 証拠の強さを分ける

得られる証拠には、強さの違いがある。

観測や相関だけより、介入や再現を含む証拠の方が、因果について強い Claim を支えやすい。

複数のデータで同じ傾向が見つかれば関係は強くなるが、それだけで元の挙動を復元できるとは言えない。

証拠が増えたことと、因果が確定したことを同じにしない。

10. Proof はどこで十分とするかを見る

Proof（成立確認）では、不確実性をすべて取り除く必要があるとは限らない。

Evidence、Claim、残っている不確実性を確認し、現在の目的に対してどこまで確かなら十分かを判断する。

この判断を Sufficiency（十分性） と考える。

証拠を増やし続けても、判断が変わらないなら追加確認の価値は下がる。

Proof は、何が確かかだけでなく、どこで十分とするかまで含めて考える。

11. green は問題がないことを意味しない

test、lint、validator、monitoring が何も問題を報告しなかったとき、green には二つの可能性がある。

問題がない場合と、問題はあるが検査で検出できていない場合である。

green は「問題がない」という観測ではない。検査で問題を検出しなかったという観測である。

検査にも可視範囲と盲点があるため、必要に応じて検査そのものも観測対象にする。

12. 観測は判断に必要な情報量で設計する

大量の処理がすべて成功したとき、一件ごとの成功ログを並べても、判断に必要な情報はほとんど増えない。

file_001 OK
file_002 OK
file_003 OK
...

この場合は、

Checked: 128442
Succeeded: 128442
Failed: 0

のように集約する。

一方、失敗したときは、件数だけでは次の判断ができないことがある。

その場合は、

  • 何が失敗したか
  • 期待値と実値はどう違うか
  • どこで失敗したか
  • 詳細をどこから追えるか

を展開する。

Success
    → 集約する

Failure
    → 判断に必要な差分を展開する
    → 必要なら raw log を参照する

raw log を残すことと、raw log をそのまま Agent に読ませることは別である。

観測は、出力できる事実の量ではなく、次の判断に必要な情報量で設計する。

13. 検査の検査には終点がいる

検査に盲点があるなら、その検査を別の検査で確認したくなる。

しかし、その検査にも盲点があるため、さらに別の検査を置くことができる。

この連鎖を完全に終わらせることはできない。

どこかで、

  • 何を検出できるか
  • 何をまだ検出できないか
  • 現在の目的にはどこまで必要か

を判断する。

この判断を Sufficiency（十分性） と考える。

検査を増やし続けるのではなく、現在の目的に対してどこで十分とするかを決める。

III. 人間に残る負担を見る

14. 作業時間を一つの時間で語らない

「速いか遅いか」は、一つの時間だけでは決まらない。

たとえば、

  • Agent が作業を終えるまでの時間
  • 結果を確認できるまでの時間
  • 人が指示や判断に使う時間
  • 依頼してから必要な結果がそろうまでの時間

は、それぞれ違う。

Agent の実行に時間がかかっても、人が待たされなければ負担は小さいことがある。

逆に、Agent が高速でも、人の確認や修正が増えれば、仕事全体が速くなったとは言えない。

Agent が作る量が人の確認できる量を上回れば、未確認の成果物がたまる。

速さを見るときは、誰のどの時間を見ているのかを分ける。

15. 人間に残る負担を三つに分けて見る

ここでは、負担を三つに分けて見る。

Human Observation Time
    結果を理解するまで
    人間が見る必要のある時間

Human Judgment Count
    作業中に
    人間へ判断が返される回数

Human Judgment Width
    一回の判断のために
    人間が扱う必要のある範囲

Agent が大量に調査や検証を行っていても、結果が整理され、人間が短時間で現在状態を把握できるなら、Human Observation Time は小さい。

小さな判断を何度も人間へ返す運用では、個々の判断が簡単でも、Human Judgment Count は増える。

判断回数が同じ一回でも、少数の選択肢と整理された根拠から選ぶ場合と、多数の成果物や未確定事項を読み直して方針そのものを作る場合では、Human Judgment Width が違う。

Agent の仕事量ではなく、人間に何が残ったかを見る。

16. 人間の思考負荷が高いなら、仕組みを疑う

正しく作業するために、人間が多くの条件を覚え、例外を追い、常に注意を張り続けなければならないなら、その負荷を人間の能力だけで吸収しない。

複雑な仕事には、考えること自体が必要な場合もある。

しかし、同じ作業を安全に行うための注意や記憶が大きすぎるなら、手順、境界、配置、表示、道具など、仕事を支える仕組みに負荷の原因がないかを見る。

判断を人間へ返すときは、認知作業の所有も見る。

人間が判断のたびに状況を再構築しなければならないなら、判断だけでなく、状況理解から判断までの認知作業そのものが人間へ戻っている。

人間が頑張ることで成立している場所は、仕組みを見直す候補になる。

IV. 仕組みと介入点を設計する

17. 仕組みを増やす条件

新しい仕組みには、追加する理由と維持する理由の両方がいる。

追加候補になるのは、たとえば、

  • 同じ失敗が繰り返される
  • 放置時の影響が大きい
  • 守る価値のある条件が明確
  • 人が何度も同じ確認・修正をする
  • 食い違いを機械的に検出できる

場合である。

追加する理由だけでなく、維持し続ける理由も見る。

18. 介入点はコストで選ぶ

同じ失敗でも、介入できる地点は一つではない。

実行前に防ぐことも、実行直後に検出することも、後工程でまとめて検査し、必要なら修正・再生成することもできる。

介入点を選ぶときは、早さだけを目的にしない。

早く介入すれば失敗の伝播を小さくできるが、待ち時間や調整が増えることもある。

一方、介入を遅らせれば、後で失敗を直す負担が大きくなる可能性がある。

介入点は、早く介入する負担と、後で失敗を直す負担を比べて選ぶ。

19. Gate は介入点に置く

まず、失敗にどこで介入するかを決める。

Gate は、その介入点に置く一つの仕組みである。

最初に「Gate を強くするか」を考えるのではない。

まず、

この失敗は
どこまで進むと高価になるか
どこなら安く見つけられるか
どこなら安く修正できるか

を見る。

小さく再生成できる成果物では、早い段階で何度も止めるより、後段で強く検証し、失敗したら捨てて作り直す方が安い場合もある。

一方、不可逆操作や他へ伝播する変更では、実行前に介入する価値が高い。

先に介入点を選び、必要な仕組みをそこに置く。

V. 境界と仕組みを更新する

20. Agent は Architecture を決めずにいる時間の価格を変える

Architecture は、早く決めても遅く決めてもコストを伴う。

早く固定すれば、まだ十分に分かっていない段階で誤った境界を作る可能性が生まれる。

一方、判断を遅らせれば探索の自由は残るが、その間に局所的な pattern が前例として増殖していく。

局所的な pattern
    ↓
Repository に現れる
    ↓
Agent が前例として参照する
    ↓
似た場所へ展開する
    ↓
さらに強い前例になる

Agent が高速に実装できる環境では、この増殖も速くなる。

したがって Architecture を決める時期は、早く固定するコストと、判断を遅らせた間に前例が増殖するコストの比較になる。

Agent 時代では、判断を遅らせる側のコストが、以前より短時間で膨らみやすい。

21. Architecture は後から変えにくい境界から先に決める

Architecture を決めないままパターンが増えるほど、後から境界を変える負担も大きくなる。

変更対象のコードだけでなく、

  • 移行の範囲
  • 旧パターンの退役
  • Agent が参照する情報の整理
  • 推論負債の解消
  • 検証のやり直し

まで必要になることがある。

ただし、これは「最初に全部決めるべき」という意味ではない。

まだ観測が不足している部分や、容易に作り直せる局所実装では、判断を保留する方が安いこともある。

一方、多数の実装が依存したあとでは変更しにくくなる境界もある。

たとえば、

  • 正本の所在
  • 管理主体
  • 依存方向
  • 状態の所有
  • 公開インターフェース
  • ファイル種別の配置

などである。

先に検討する価値が高いのは、増殖したあとで変更すると高くつく境界である。

22. 人間と仕組みの境界は時間とともに動く

仕事の中には、最初は人間にしか判断できないことがある。

たとえば、

  • どこまで磨けば十分か
  • どの近道を許容するか
  • この構造を将来のリスクと見るか
  • どこまで確認すれば完了とするか
  • この違和感を修正対象とするか

といった判断である。

安定した判断は仕組みへ移せるようになり、まだ一般化できない判断は人間に残る。人間と仕組みの境界は、その繰り返しによって動いていく。

23. 仕組みに移した判断は、永久に正しいとは限らない

環境、モデル、Repository、目的、コスト構造が変われば、以前は有効だった規則が新しい仕事を妨げることがある。

判断
    ↓
安定する
    ↓
仕組み
    ↓
環境が変わる
    ↓
再評価
    ↓
維持 / 修正 / 廃止 / 判断へ戻す

したがって、規則化は判断の終了ではない。

仕組みに移した判断も、環境が変われば再び人間の判断へ戻ることがある。

24. 再評価は追加だけでなく削除を含む

仕組みは、作った時点の問題や制約を前提にしている。

重要なのは、仕組みが現在も存在していることではなく、それを追加した理由が現在も存在しているかである。

再評価するときは、

  • 何を防ぐために追加したのか
  • 問題や制約は今も存在するか
  • 外しても必要な状態を維持できるか
  • 残すことで新しい負担や不整合を生んでいないか

を見る。

再評価は追加だけでなく、削除を含む。

25. 移行より作り直しが安いことがある

既存実装を新しい設計へ移すとき、常に段階的な移行が安全とは限らない。

特に、小さく再生成可能な道具では、旧実装を少しずつ修正することで、かえって旧世界と新世界が長く共存することがある。

旧方式
    +
新方式
    ↓
両方が Repository に残る
    ↓
両方が推論候補になる
    ↓
比較・例外・移行処理が増える

この状態は、実装上の複雑さだけでなく推論負債も増やす。

小さく再生成可能な道具では、scrap-and-build を選べることがある。

26. 変更対象とは別に制御経路を持つ

現在使っている制御経路そのものを変更するとき、その経路だけに復旧を依存させない。

今から切る電線を使って、電線を切る命令を送らない。

変更前に別の制御経路を成立させ、その経路から対象を観測できることを確認する。

VI. 判断と責任を分ける

27. 実装を外すと判断の生産が露出する

Agent が code、test、documentation、CI、tool、review artifact を生成するようになると、人間の実装作業量は減る。

しかし、それだけで人間の仕事そのものが消えるわけではない。

何をやるか
何を良しとするか
何を境界にするか
なぜ仕事が閉じなかったか

まで自動的に Agent の判断になったわけではないからである。

実装を人間から外すと、それまで実装作業の中に埋もれていた別の仕事が見えやすくなる。

ここでは、成果物を誰が生成したかと、その仕事を成立させる判断を誰が作ったかを分けて見る。

agent-generated
        ≠
agent-decided

したがって Agent 化を見るときは、どれだけ実装を自動化したかだけでなく、どの判断が、誰によって、どこで生産されているかを見る。

28. Role と Actor は分けて考える

仕事の中に異なる役割があるからといって、必ず異なる Agent が必要とは限らない。

たとえば、

  • 実装
  • 確認
  • 整理
  • 手入れ
  • 保守

という役割があるとする。

これらをそのまま、

実装 Role
    → 実装 Agent

確認 Role
    → 確認 Agent

整理 Role
    → 整理 Agent

と対応させる必要はない。

Role は何に責任を持つかを表し、Actor は誰がその責任を担うかを表す。

Role が違う
    ≠
Actor も違う

一つの Actor が、複数の Role を順番に担うこともできる。

逆に、一つの Role を複数の Actor に分担させることもできる。

役割が違うなら Agent も分けるべきだ、という発想だけで Agent を増やさない。

29. Actor を増やすコストを見る

Agent を増やすと、

  • 文脈の引き継ぎ
  • 調整
  • 状態の共有
  • 権限の分割
  • 結果の統合

といった別のコストが発生する。

たとえば、作業を終えた後に Repository を見直す責任が必要だからといって、必ず 整理 Agent を新設する必要はない。

同じ Agent が、実装 Role を終えたあとに整理 Role へ切り替えてもよい。

重要なのは、Actor の数ではなく、必要な責任が明示され、混ざらずに実行されることである。

Role は責任の単位であり、Actor はその責任を担う主体である。Role を分けることと、Actor を増やすことは別の設計判断である。

30. 責任を時間で分ける

必要であることと、今実行すべきことは同じではない。

現在の責任でなければ、その場で仕事を広げるのではなく、後の時間へ渡す。

これは責任を捨てることではない。

責任を、実行すべき時間へ配置することである。

作業中は現在の目的に集中し、作業後や定期的な振り返りでは、今回の仕事が将来の作業へ何を残したかを見る。

責任は、同時に抱える必要はない。時間を分けて実行できる。

VII. 知識と作業を次へ渡す

31. Repository は Prompt Surface である

Agent に対する Prompt は、チャットなどの指示だけではない。

Agent が見ることのできる、

  • コード
  • テスト
  • コメント
  • ファイル名
  • ディレクトリ構成
  • 古い実装
  • 回避策
  • ドキュメント
  • 生成物

も、すべて推論材料になる。

つまり、

Agent が見えるもの
    ↓
推論候補になる
    ↓
指示として作用する

と考えられる。

この意味で、Repository は単なる code storage ではなく、Prompt Surface である。

重要なのは、Repository に存在するものが、現在も正しいかどうかを判定されてから Agent に見えるわけではないことである。

Agent に何を言うかだけが Prompt ではない。Agent に何を見せているかも Prompt である。

32. 知識へのアクセス経路を残す

知識を整理すると、答えは残っても、そこへ辿り着いた経路が消えることがある。

記録には、

困った
  ↓
ここを見た
  ↓
これが分かった
  ↓
次はここを見る

という形で、知識そのものだけでなく、知識へのアクセス経路が残る。

この経路があれば、次に似た問題へ出会った人や Agent は、答えだけでなく、どの症状からどの情報へ進めばよいかを再利用できる。

答えだけでなく、答えへ辿る経路を残す。

33. 作業は、再開できる単位でそろえる

変更の結果だけを残しても、再開に必要な材料が離れていると、あとから別の探索が必要になる。

設計書、コード、検証結果、実行に必要な生成物など、同じ作業から生まれたものは、可能な限り同じ作業単位でそろえて残す。

ここでそろえるとは、必ず同じフォルダに置くことではない。

対応関係と所在がたどれ、どれが正本か迷わない状態にする。

作業は、成果だけでなく、再開に必要な組をそろえて閉じる。

34. 失敗、成功、幸運を分けて振り返る

振り返りを失敗だけに寄せると、変更、禁止、抑止を増やす方向へ偏りやすい。

そこで、結果を少なくとも三つに分けて見る。

失敗した
    → 何を変えるか

うまくいった
    → 何を残すか

運がよかった
    → 何を仕組みに変えるか

うまくいったことと、運がよかったことは同じではない。

意図した設計や仕組みによって成立したなら、それは残す候補になる。

一方、偶然の人間介入、たまたま残っていた余裕、偶然通れた経路によって助かったなら、その成功を、そのまま再現可能とはみなせない。

結果がよかったことだけで判断せず、なぜその結果になったかを見る。

失敗からは変えるものを、成功からは残すものを、幸運からは仕組みにするものを拾う。
